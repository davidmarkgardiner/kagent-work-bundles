Story 1 · Desired architecture · 02 / 07

Keep the team contract small. Give each layer a clear job.

The platform should preserve a familiar API experience while adding durable state and a choice of execution. Compatibility across the classic and newer runtime families must be proved.

Orchestration and durable task/session records

Own progress, evidence references, approvals, tool-call identity, and recovery decisions. Decide what runs next and whether a side effect may proceed.

Execution

Run the agent in an approved runtime. Pilot Substrate actors for isolated execution and supported snapshot/restore.

A shared worker pool supplies active capacity. Snapshot storage retains configured durable state between activations. The documented kagent DATA mode restarts the process rather than preserving RAM.

Memory and knowledge

Keep session history, scoped facts, curated shared lessons, and cited procedures separate.

Persistent stores and bounded retrieval provide context. They do not decide authorization or replace current evidence.

Models and MCP tools

Agent Gateway mediates supported model and tool paths with per-hop identity, explicit operations, usage controls, and telemetry.

The resource behind each adapter still enforces its own permissions.

Cross-cutting operations. Correlate task, session, actor, approval, memory, and tool-result identities through OTel and LGTM. Apply quotas, evaluation, retention, and controlled rollout across the layers.
Runtime names and migration boundaries

The newer kagent API uses Harness and AgentTemplate configuration rather than treating this as an image-tag change to the classic deployment. Substrate Actor and ActorTemplate are runtime API records; WorkerPool is a Kubernetes CRD. KRO does not directly create every session actor as a Kubernetes child.

Substrate supplies execution and lifecycle mechanisms. The application and orchestration layer retain workflow decisions, approvals, and external-effect reconciliation. Durable task storage and scoped memory can be developed before adopting an actor runtime.

Story 1 · Desired shared-platform security · 03 / 07

Entra grants identity. The platform enforces the boundaries.

Entra provides the badge. Gateway checks it at each API boundary. Kubernetes controls the workload, its API permissions, and its network paths.

Outside Kubernetes · Entra identity control plane

Who is the caller?

Human or application identity, workload federation, and the approved agent identity.

What may it request?

API registrations, audiences, application roles or delegated scopes, and explicit grants.

What is issued?

A token for the intended API. Kubernetes RBAC alone cannot create these Entra permissions.

Inside the Kubernetes platform

Agent Gateway checks each request.

Validate token signature, issuer, audience, expiry, identity, and permitted capability. Caller → agent and agent → MCP are separate requests with separate credentials. The MCP/backend also checks the target resource.

Routing and request policy

Gateway and allowedRoutes control listener attachment. HTTPRoute selects the destination. AgentgatewayPolicy enforces request permission.

ReferenceGrant permits a cross-namespace backend reference where needed. It does not authenticate the caller.

Workload and API rights

ServiceAccount, Role, and RoleBinding constrain Kubernetes API authority. Admission and pod-security rules constrain what can run. Quotas and limits bound capacity.

Agent definitions and runtime resources remain platform-governed; an actor runtime adds its own isolation boundary.

Network and bypass control

Enforced NetworkPolicy or approved CNI controls restrict traffic to the agent, controller, MCP, and model paths.

Block direct backend access and alternate ingress. Mandatory controls must remain outside the caller team's ability to remove or weaken them.

An approved caller may invoke one agent. That agent needs its own tool permission. A token, route, or namespace is never a blanket grant.

Standard NetworkPolicies are additive. Full namespace administration requires stronger platform ownership and admission boundaries than the classic demo's restricted customer-request role. Verify both allowed paths and bypass denials in the receiving environment.

Story 1 · Illustrative desired behaviour · 04 / 07

Pause the work without losing what it means.

A task can outlive a request, a worker, or an approval wait. Its durable record must explain what happened and what is allowed next.

→
Wait for approvalKeep the decision bound to this task and proposed change.
→
Resume safelyRestore context, verify authority, and reconcile effects.
Inspect an intended continuity stage
Intended state

Record a recoverable point.

Persist the task and session IDs, completed steps, evidence references, tool-call IDs, and proposed next action.

Save the configured actor snapshot only at a safe, supported boundary. Check the required snapshot fidelity and durability completion.

WHAT SHOULD SURVIVE

The recovery record identifies the original work and last confirmed effects. It can distinguish completed, pending, and uncertain operations after an interruption.

A snapshot alone is not a durable workflow ledger.

Intended state

Wait with the approval contract intact.

Bind the decision request to the task, proposal, evidence, intended approver, and relevant revision. Persist expiry, denial, and cancellation states.

Where supported and safe, suspend the actor and release its worker assignment.

WHAT REMAINS ALLOCATED

The task and snapshot remain stored. A worker can serve other actors, but the warm pool, databases, and storage still have costs. Suspending an actor does not automatically remove a node.

Intended state

Continue the same approved work.

Restore supported state onto available capacity. Validate the approval and revision, refresh credentials where needed, and recheck time-sensitive evidence.

Read back an uncertain external write before deciding whether to retry. Preserve the tool-call identity and attempt history.

WHAT MUST STILL BE CHECKED

Permissions, current backend state, remaining budgets, and the intended action. Restoring a snapshot does not undo a Git change, ticket, database write, or other external effect.

The target does not assume exactly-once execution.

The documented kagent DATA snapshot mode restores durable directories and restarts containers; it does not preserve process RAM. Full memory restoration is a separate runtime capability to validate for the chosen integration.

Keep workflow durability, approval authority, and actor restoration as separate checks that work together.

Story 1 · Governed memory and learning · 05 / 07

Remember useful evidence. Keep its scope and source.

Memory should help an agent investigate and explain. Recalled information must be checked against current reality before it supports a decision.

Session history

The conversation, task progress, and handoff references needed to continue one thread. Store them durably and retain the correct session identity across recovery.

Scoped semantic memory

Selected facts and preferences retrieved by relevance within the permitted agent and user scope. Bound the result size, age, and context added to the model.

Curated shared lessons

Prior incidents, decisions, verified outcomes, and evidence links. Agents use read-only search; a curator validates proposals and writes transactionally with an audit trail.

Cited runbooks and skills

Reviewed procedures remain in Git or another approved source. Retrieval supplies citations. A successful incident lesson can become a proposed documentation or skill update.

Retrieve narrowlyApply identity and scope filters before returning relevant records.
→
Verify nowCheck fresh evidence and whether the prior lesson still applies.
→
Curate the outcomeRecord provenance, review, expiry, supersession, and deletion.
Actor snapshots preserve configured runtime state. Semantic memory retrieves knowledge. Neither grants permission to perform a change.

The target includes tenant isolation, retention and deletion rules, bounded reads, and no secrets in remembered records. It does not allow unrestricted self-modification or automatic cross-agent sharing of native memory.

Current evidence and the next memory proof

The shared-context bundle defines the desired test, but contains an evidence template rather than a completed receiving-system receipt. The current graph POC and the PostgreSQL-backed, curator-controlled production design have different durability and concurrency properties.

Prove cross-session recall, restart survival, false-match rejection, denied cross-scope access, concurrent writes, provenance, and deletion before promoting the target.

Story 1 · Intended value and how to measure it · 06 / 07

The business case is wider than compute cost.

Each capability needs an observable outcome. The measures below are evaluation targets, not results claimed by this demonstration.

Continuity and reliability

Recover progress after a supported interruption and preserve the identity of work waiting for a person.

Measure recovery success, lost progress, recovery time, and manual intervention.

Security and governance

Combine execution isolation with scoped identities, tool permissions, controlled memory writes, and enforced approvals.

Measure denied cross-scope access, unauthorized effects, and approval-binding failures.

Quality and reuse

Find attributable prior evidence, reject stale or irrelevant matches, and promote accepted lessons through review.

Measure cited-answer quality, false matches, repeat-investigation time, and accepted lessons.

Responsiveness and capacity

Restore actors onto prepared workers where supported and share capacity across intermittent sessions.

Measure restore latency, queue delay, utilization, and concurrent demand.

Developer experience

Let teams consume a governed agent API and approved capabilities without designing their own persistence and execution stack.

Measure onboarding time, integration effort, support burden, and workflow adoption.

Total cost and efficiency

Aim to reduce repeated investigation, duplicate calls, unnecessary context, and idle actor allocations.

Compare model and tool usage, warm pools, databases, embeddings, snapshots, and operator effort.

Operational audit supports every outcome. Connect the request to its task, actor, approval, memory evidence, tool result, and Git revision. Record missing telemetry rather than inventing a complete trace.
Supported suspension can release an actor's worker. It does not eliminate model tokens, pool overhead, storage cost, or the need to operate the system.

Story 1 · A staged route to the desired product · 07 / 07

Prove the layers, then prove the service.

Build on the secure API foundation. Add each capability with receiving-system evidence before opening it to more teams.

  1. Secure API foundation

    Keep the reviewed definition, protected route, explicit tools, and verification. Add Entra integration and prove denied network and backend paths in the receiving environment.

  2. Durable task and session proof

    Interrupt safe work, restart during an approval wait, and recover original identities. Reconcile an uncertain external mutation before retrying.

  3. Scoped memory and curated learning

    Prove restart survival, bounded useful recall, isolation, write concurrency, provenance, retention, and deletion using synthetic records.

  4. A separate actor-runtime pilot

    Select a compatible version pair and one suitable workload. Test snapshot fidelity, durability, denied access, credential renewal, restoration, and cleanup.

  5. Integrated recovery and value

    Run the real API-to-agent-to-tool path with approvals and fault injection. Compare safety, recovery, quality, total cost, and operator effort against the baseline.

  6. Wider self-service

    Offer approved profiles, clear quotas, support ownership, and versioned rollout and rollback. Preserve the small team contract and prove API compatibility.

Durable state and governed memory can advance before Substrate adoption. Add actor execution where its measured value justifies the operational cost.
What we have actually established so far
  • The 4 November classic receipt records native deployment, model/caller PONG, and JWT controls. It is not an integrated durable-memory proof.
  • The 7 October disposable AKS evaluations recorded actor/card lifecycle restores. They did not test model, MCP, chat, or changed-data recovery. Those evaluation resources were deleted.
  • The Infinity fixture demonstrates retained-history continuation within one process. It does not prove process-crash recovery or integration with Substrate.
