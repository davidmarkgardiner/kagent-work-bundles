# Monday demo sheet: the components and policies of a secure agent service

**Walkthrough order:** model configuration → skills/tools → native Agent → KRO
composition → Gateway/routing → policies → Kubernetes boundaries → live proof.
Reference versions: **kagent 0.10.4**, **KRO 0.9.4**, **agentgateway 1.7.0**.
This is a component inventory, not an instruction to deploy every option.

**Usage labels:** **Demo** = created by this composition or its platform baseline;
**Reuse** = existing backend/platform resource or native controller output;
**Option** = available configuration requiring its own setup and validation;
**Next** = planned identity integration. These labels are not live test results.
Install CRD definitions once; deploy their custom-resource instances as needed.

## 1. kagent: what the agent is allowed to use

Active native Agent, ModelConfig and RemoteMCPServer references use
`kagent.dev/v1alpha2`. Skills, prompts and tool lists are fields, not separate CRDs.

| Component | What it does / why it matters | Usage |
| --- | --- | --- |
| **ModelConfig** | Selects model, provider, endpoint and provider options, with credential references. Point it at the approved model Gateway. It is the agent's model client configuration, not the Gateway's entire model garden. | Reuse |
| **Skills: `Agent.spec.skills`** | Loads reviewed Git/OCI/S3 skill sources into `/skills`, with source authentication where required. Use immutable commits/digests and approved fetch egress. Skills may enable executable behavior; they are not a security boundary. | Option; catalog examples |
| **System prompt: `spec.declarative.systemMessage`** | Defines task, scope and behavior. Supplied through the customer instance and passed into the native Agent. Prompt instructions do not replace authorization. | Demo |
| **Agent** | Declares the runtime, prompt, ModelConfig, skills, selected tool bindings and deployment settings. kagent reconciles the ordinary runtime Deployment and Service. | Demo |
| **kagent controller** | Shared reconciler/control API, model/tool discovery and session/task storage integration. Its approved PostgreSQL service and controller ingress protection are platform dependencies, not extra customer fields. | Reuse |
| **RemoteMCPServer** | References an existing MCP URL, transport, TLS and header/credential sources. Backend identity and permissions remain enforced by the server and Gateway. | Reuse for tool scenarios |
| **Native MCP tool bindings / `toolNames`** | Exposes explicit operations to the agent instead of an unrestricted tool catalog. The selected name alone does not grant backend permission. | Demo composition; backend tests separate |
| **`allowedNamespaces` on Agent/RemoteMCPServer** | Restricts cross-namespace agent-as-tool or MCP references where supported. Distinct from Gateway allowedRoutes, ReferenceGrant and network access. | Option |
| **ModelProviderConfig** | Provider endpoint and credential reference, with discovered-model status. Useful for provider/model discovery; not required for this composition's existing ModelConfig reference. | Option |
| **ToolServer / Memory** | Additional legacy kagent APIs for tool configuration and provider-backed memory. Verify their served version and actual runtime integration before using. Memory is not automatically a knowledge-base ingestion service. | Option / legacy |
| **Knowledge base / retrieval service** | Reviewed reference content may be supplied as skill files; indexed search/RAG requires an actual retrieval/index service and its tool/identity contract. Do not imply Markdown alone creates retrieval. | Option / external service |
| **SandboxAgent / AgentHarness** | Additional 0.10.4 CRDs for Substrate execution paths. Their installed definitions do not mean their runtime is installed. They are not used for this native Deployment demo. | Outside this demo |
| **MCPServer from kmcp** | Optional separate controller's server lifecycle resource. Distinct from a RemoteMCPServer reference to an already running endpoint. | Option / separate controller |

Do not mix in 1.x `api.kagent.dev` AgentTemplate/Harness manifests. That is a
different API/runtime family, not a prerequisite for this secure-agent recipe.

## 2. KRO: how one customer file assembles the service

| Component | What it does / why it matters | Usage |
| --- | --- | --- |
| **ResourceGraphDefinition**, `kro.run/v1alpha1` | Platform-owned schema, catalog mapping, resource templates, CEL expressions and dependencies. Reconciles the Agent and surrounding objects. | Demo |
| **ClassicSecureAgent**, `demo.kagent.dev/v1alpha1` | The custom instance generated by this RGD. Customer inputs are modelConfig, systemPrompt, skills and tools. This kind belongs to this demonstration, not upstream kagent. | Demo; one customer file |
| **Schema constraints / CEL / `readyWhen`** | Validate allowed choices and readiness. The caller route depends on successful Golden completion. This is orchestration logic, not a separate policy CRD. | Demo |
| **Golden ConfigMap + Job** | Fixed verification configuration and a separate verifier identity. Checks the AgentCard, denied requests and one real model PONG. The receipt identifies this owner UID and native task. | Demo |
| **KRO controller, its RBAC and customer RBAC** | Shared graph reconciler. The platform permits it to manage children while customers manage only approved instances. Prevent customers modifying policies or minting privileged identities through child-resource access. | Required platform setup |

KRO's resource graph is not an Azure ResourceGroup. Azure ResourceGroup/ASO
resources belong to a separate infrastructure-provisioning demonstration if needed.

## 3. Gateway API and agentgateway: where traffic may go

Gateway API resources use `gateway.networking.k8s.io`; agentgateway's own CRDs
use `agentgateway.dev/v1alpha1` in the pinned installation.

| Component | What it does / why it matters | Usage |
| --- | --- | --- |
| **agentgateway controller + proxy workload** | The controller translates accepted CRDs into configuration; the data-plane proxy handles real requests, authentication, policy, routing and telemetry. Controller readiness alone does not prove a request is protected. | Reuse controller; baseline creates dedicated proxy |
| **GatewayClass** | Selects the responsible Gateway controller and optional parameters. Usually shared platform setup. | Reuse |
| **Gateway + listeners + `allowedRoutes`** | Defines listener ports/protocols, certificates and which namespaces may attach Routes. The demo separates verifier and caller listeners. allowedRoutes controls configuration attachment, not caller authentication. | Demo / shared class |
| **HTTPRoute** | Matches host/path/method/headers, selects a backend and applies routing filters. The demo has AgentCard, verifier and post-Golden caller routes. | Demo |
| **Route filters** | Request/response header changes, URL rewrites, redirects and other supported Gateway API filters. Do not strip required identity or introduce a bypass. Mirroring can duplicate sensitive or chargeable operations; it is not enabled by this demo. | Rewrites in demo; others optional |
| **ReferenceGrant** | Backend-namespace consent for specified cross-namespace references. Restrict source namespace/kind and destination resource. It is not JWT authentication, RBAC or network permission. | Conditional; unnecessary for this same-namespace backend layout |
| **GRPCRoute / ListenerSet** | Additional gRPC routing and delegated listener configuration when the installed Gateway API/controller supports them. | Option |
| **AgentgatewayBackend** | Represents supported AI, MCP, A2A, static or other upstream targets and their backend settings. A route can also target the native agent's Kubernetes Service directly, as this demo does. | Reuse / option |
| **AgentgatewayModel** | Gateway model-garden entry: concrete provider model or virtual model, matching/visibility, policies, and supported weighted/failover/conditional/callout routing. Distinct from kagent ModelConfig. | Reuse existing catalog / option |
| **AgentgatewayParameters** | Configures proxy workloads, service, images, resources, scaling, disruption budget, logging and supported model-catalog/SPIFFE settings. Not a request authorization policy. | Platform option |
| **InferencePool** | Gateway API Inference Extension resource for compatible self-hosted inference routing; requires its own extension setup. | Option / separate extension |

## 4. AgentgatewayPolicy: the policy menu

These are **fields/families within AgentgatewayPolicy**, not a separate CRD for
each row. Attach using local `targetRefs` or `targetSelectors`, with valid
listener/route-rule sections where supported. Legal targets vary by field.
Inspect policy **Accepted/Attached** status and the effective configuration.

### Frontend policies: connections arriving at the Gateway

| Policy/configuration | What it provides | Usage |
| --- | --- | --- |
| `frontend.tls` | TLS protocol/cipher/handshake settings. HTTPS certificates are referenced by Gateway listeners. Incoming mTLS client validation is Gateway `spec.tls.frontend` configuration and requires Gateway API 1.5+. | Option; not demonstrated by the HTTP lab listeners |
| `frontend.tcp`, `frontend.http` | Connection, concurrency, header, buffering and idle/lifetime limits to bound resource consumption. | Option |
| `frontend.networkAuthorization` | CEL rules on downstream connection attributes. Complements, rather than replaces, Kubernetes NetworkPolicy and request authorization. | Option |
| `frontend.accessLog` | Access-log fields, filters and OTLP export. Redact credentials and sensitive prompt/tool content. | Reuse existing telemetry / option |
| `frontend.tracing`, `frontend.metrics` | OTel sampling/export/attributes and custom Prometheus labels. Correlate Gateway, agent/model and MCP activity. | Reuse existing telemetry / option |
| `frontend.proxyProtocol`, `frontend.connect` | Trusted proxy metadata and explicit HTTP CONNECT behavior. Enable only for a reviewed topology; do not create an open proxy. | Option |

### Traffic policies: who can invoke which request

| Policy/configuration | What it provides | Usage |
| --- | --- | --- |
| `traffic.jwtAuthentication` | JWT issuer/JWKS, audience and validation mode. The demo uses Strict validation and separate verifier/caller identities. Entra can be a later approved issuer integration. | Demo; Entra integration Next |
| `traffic.authorization` | CEL decisions using validated identity, claims and request attributes. Enforces the exact caller or verifier subject in this demo. | Demo |
| `traffic.apiKeyAuthentication`, `basicAuthentication` | Alternative supported credential schemes with configured credential sources. Basic auth needs TLS; neither automatically establishes Entra identity. | Option |
| `traffic.extAuth` | External HTTP/gRPC authorization for centrally managed decisions. Configure timeouts and failure behavior explicitly. | Option / external authorization service |
| `traffic.extProc` | External request/response processing. Requires an actual processor and explicit failure/processing settings. | Option / external processor |
| `traffic.rateLimit.local`, `.global` | Request or LLM-token budgets, optionally keyed by identity/team/model. Local counters are per proxy replica; global limits require a coordinating service. | Option |
| `traffic.cors`, `.csrf` | Browser-origin handling and CSRF protection for applicable browser/cookie flows. CORS is not authentication. | Option |
| `traffic.headerModifiers`, `.hostRewrite`, `.transformation` | Header, host and request/response transformations. Preserve identity semantics and avoid logging or forwarding unintended credentials. | Option |
| `traffic.buffer`, `.timeouts`, `.retry` | Bounded buffering and deadlines, plus explicitly configured retries. Retrying an agent/model/write request can duplicate actions or spend; Golden does not automatically retry inference. | Option |
| `traffic.directResponse`, `.delay` | Explicit immediate responses and controlled fault/latency injection. Useful for testing, not proof of a model response. | Option |
| `traffic.phase`, conditional execution, `strategy.inheritance` | Request-processing placement, conditions on supported policy fields, and traffic-policy inheritance. `Default` permits more-specific overrides; `Override` makes a less-specific traffic policy authoritative over lower attachment points. | Option; review effective security policy |

Token budgets use observed model usage and can be charged after completion;
they are not a hard mid-generation cutoff. Provider output-token limits are a
separate control. A pricing catalog plus observed usage can support cost reporting;
do not present a soft token budget as an exact financial spending guarantee.

### Backend policies: how the Gateway accesses models, agents and tools

| Policy/configuration | What it provides | Usage |
| --- | --- | --- |
| `backend.auth` | Secret-backed credentials, approved token passthrough, Azure/AWS/GCP authentication, additional credential injection, signed JWTs, OAuth token exchange and supported cross-app identity exchange. Choose a supported flow; do not assume user delegation happens automatically. | Reuse approved provider auth / option |
| `backend.auth.azure` | Supported managed-identity/Workload Identity credential acquisition and scopes. Entra app registrations, federation, audience, UAMI assignment and backend grants are separate setup. | Next for this composition |
| `backend.authorization`, `.extAuth` | Access decisions after a destination backend is selected; optional external checks. | Option |
| `backend.tls` | Server CA/SNI/SAN verification and optional outbound client certificates or SPIFFE identity. Do not use insecureSkipVerify as a security default. | Option; backend-dependent |
| `backend.tcp`, `.http`, `.tunnel` | Backend connection/keepalive settings, response deadline/protocol selection and approved outbound proxy tunneling. | Option |
| `backend.health`, `.sessionAffinity` | Backend health/eviction and supported best-effort affinity. Availability controls do not authorize a caller. | Option |
| `backend.transformation` | Destination-specific request/response mutation. | Option |
| `backend.ai.defaults`, `.overrides`, `.transformations`, `.finalTransformations` | Provider-request defaults, enforced overrides and CEL body transformation. Useful for reviewed generation limits and provider parameters. | Option |
| `backend.ai.prompt`, `.modelAliases`, `.routes`, `.promptCaching` | Prompt enrichment, friendly model names, supported AI API route mappings and provider-dependent prompt caching. These are not authorization by themselves. | Option |
| `backend.ai.promptGuard` | Request/response regex checks and supported moderation/guardrail integrations: OpenAI moderation on requests, Bedrock Guardrails, Google Model Armor and webhooks. External products need their own credentials/service/configuration. | Option; not proof of complete prompt-injection prevention |
| `backend.mcp.authentication` | MCP-specific authentication and OAuth metadata behavior. Its combination with traffic JWT settings has schema restrictions; validate the exact design. | Option |
| `backend.mcp.authorization` | Restricts exposed/callable MCP tools using the supported policy. Complements the Agent's explicit tool list and the backend's real permissions. | Option |
| `backend.mcp.guardrails` | CEL or remote processors for MCP requests/results, such as bounded arguments and data handling. An actual backend operation still needs authorization. | Option |

## 5. Kubernetes and supporting services: enforce the boundary underneath

| Object/control | What it does / why it matters | Usage |
| --- | --- | --- |
| **Deployment / Pod / Service** | The native agent's actual runtime and reachable service. kagent owns their lifecycle; KRO owns the Agent resource. A Service routes traffic but does not authenticate it. | Native controller output |
| **Namespace + labels** | Organizes tenancy, allowedRoutes selectors and policy selection. A namespace alone is not isolation. | Demo / platform |
| **ServiceAccount + projected service-account token** | Separate runtime, verifier and caller identities. Disable default token automount; project only needed audience/expiry tokens. kagent separately projects its own controller-audience token. | Demo |
| **Role / ClusterRole + RoleBinding / ClusterRoleBinding** | Kubernetes API permissions for controllers, customers and tool identities. Chat access is not Kubernetes write permission. Golden itself gets no API Role/Binding in this recipe. | Platform / backend setup |
| **NetworkPolicy** | Approved Gateway ingress and DNS/model/controller/MCP egress. Requires an enforcing CNI and real denied-traffic tests. Also protect controller and backend bypass paths. | Demo intent; traffic proof required |
| **Pod/Deployment security settings + Pod Security Admission** | Non-root user, no privilege escalation, dropped capabilities, RuntimeDefault seccomp, read-only root, restricted writable volumes, requests/limits. PSA is namespace labels/admission behavior, not a dedicated custom resource. | Runtime settings in demo; PSA platform option |
| **Secret / ConfigMap / certificate references** | Credentials and configuration. Secrets require appropriate RBAC, encryption-at-rest configuration and rotation; a Secret object is not automatically a vault. Keep token values and model keys out of customer YAML. | Demo configuration / reused credentials |
| **ResourceQuota / LimitRange** | Namespace capacity limits and workload defaults. | Option |
| **ValidatingAdmissionPolicy + Binding** | Native admission CEL constraints for allowed images, security fields and ownership contracts. Distinct from Gateway request CEL. | Option |
| **Kyverno Policy/ClusterPolicy or Gatekeeper constraints** | Additional admission validation/mutation, image verification and policy reporting with the chosen engine. Not installed by this composition. | Option / separate controller |
| **HPA / PodDisruptionBudget / probes / PVC** | Runtime resilience, bounded scaling and persistent data where needed. kagent 0.10.4 needs its approved PostgreSQL service; the bundled demo database is not the workplace database design. | Native/shared resources; extra resilience optional |
| **cert-manager Certificate/Issuer; ExternalSecret/SecretStore; SecretProviderClass** | Optional certificate/secret lifecycle integrations, each requiring its respective controller/provider. | Option / separate integrations |
| **OTel collector; ServiceMonitor/PodMonitor/PrometheusRule** | Telemetry collection, scraping and alerting through the existing platform. Operator-managed forms require their respective CRDs/controllers. | Reuse existing observability / option |
| **Entra application/service principal, UAMI and federated credential** | Cloud identity and federation for approved callers/workloads. These are not native Kubernetes objects merely because a ServiceAccount references them; optional ASO resources can manage Azure infrastructure separately. | Next / platform identity setup |

## 6. What to show on Monday

1. Open the customer's one YAML, the RGD and the native Agent. Identify reused
   models/tools versus generated security objects.
2. Show Gateway listener protection, route JWT/CEL policy, network intent and
   the matching Golden receipt. Prove allowed caller PONG and denied callers.
3. Show one approved tool read plus actual tool/audit evidence, selected model,
   policy decisions, traces and real token counters where configured.
4. Mark every optional control **configured / tested / not configured / blocked**.
   Installed CRDs, Accepted policies and presentation playback are not runtime proof.
