How our agents
stay isolated.

An HTTPRoute selects a destination. Isolation comes from who can use that route, what the destination permits, and whether callers can bypass the gateway.

Where does it go?The HTTPRoute selects the approved agent or MCP backend.

Is this call allowed?Identity policy, tool permissions, and backend controls decide.

Design explanationThis page describes the intended shared-cluster contract. It is not evidence that the workplace configuration or Entra flow has passed runtime verification.
01

Two requests. Two permission checks.

The caller asks a named agent for help. That agent makes a separate request to its approved tools using its own identity. Both requests pass through the platform gateway.

Platform-controlled accessApproved request pathDenied path

Request 1 / incoming A2A

May this caller invoke Agent A?

  1. The caller obtains a token for the protected A2A API.
  2. The gateway validates the token and the approved caller-to-agent mapping.
  3. The route forwards to the exact Agent A endpoint.

Request 2 / outgoing MCP

May Agent A use this tool?

  1. The running agent obtains its own token for the protected MCP API.
  2. The gateway checks that identity, the destination, and the permitted capability.
  3. The MCP adapter checks arguments and enforces downstream resource permissions.

An incoming permission does not become an outgoing permission

A caller may invoke Agent A while Agent A has only read access to a specific MCP tool. Calling Agent A does not grant access to Agent B, write tools, or other teams' resources.

02

What each control actually does

These controls answer different questions. A valid route and a reachable Service do not establish permission to invoke an agent or tool.

ControlQuestion it answersOur design
HTTPRouteWhere does a matching request go?The platform owns routes with fixed matches and named agent or MCP destinations.
Gateway allowedRoutesWhich namespaces may attach routes to a listener?Shared listeners accept routes only from approved platform-controlled namespaces.
ReferenceGrantMay a route reference this backend across namespaces?The destination owner grants a reference from the platform route namespace to a named target. This does not authenticate callers.
Identity and access policyWho may invoke this agent, MCP, or capability?Validate signature, issuer, audience, expiry, identity, role, and approved destination. Deny requests without an access grant.
MCP tool and resource checksWhat operation may reach which resources?Restrict tool discovery and calls. Validate resource arguments and use a narrowly scoped downstream identity.
Network and admission controlsCan a workload bypass or weaken these checks?Protect backends and controller APIs from direct access. Keep mandatory cross-team enforcement outside team control.

Route attachment to a Gateway uses allowedRoutes. A cross-namespace backend reference uses ReferenceGrant. They are separate handshakes.

03

Namespace scope and ownership are separate

An HTTPRoute is namespaced. In our design it lives in a platform namespace, even when it sends traffic to an agent in a team namespace.

The team manages its namespace

Teams retain namespace-scoped administration through their CLI or delivery pipeline.

  • Agent behaviour, prompts, and application code.
  • Application Deployments, Services, and configuration.
  • Namespaced resources within the team's approved authority.

This authority does not extend to other teams, platform namespaces, or cluster-scoped objects.

The platform protects shared access

Shared permission enforcement lives outside the team's administrative control.

  • Gateway listeners, HTTPRoutes, and access policies.
  • Shared backend configuration and protected credentials.
  • External identity grants and mandatory cluster-level controls.

The destination owner approves backend references and downstream capability access. Team-editable objects cannot grant authority over another namespace.

A team administrator is inside that team's trust boundary.

A namespace administrator can change namespaced policies, launch Pods with available ServiceAccounts, and read namespace Secrets. Do not place credentials with broader authority there. Standard NetworkPolicies are additive, so isolation cannot rely solely on policies the same administrator can change.

04

What happens when access is attempted?

These are the required outcomes to verify in the target environment. They describe the design contract, not a live test result.

ALLOWApproved caller invokes Agent A.

The gateway validates the caller and forwards the request to the named agent endpoint.

ALLOWAgent A uses its approved read tool.

Its own MCP token, the named tool, and the requested resource scope must all pass validation.

DENYAgent A requests unapproved Agent B.

Agent A needs a separate A2A permission grant. An MCP token or shared cluster membership grants no such access.

DENYA permitted tool targets another team's data.

The adapter and downstream identity reject the resource target even if the tool name itself is allowed.

DENYA team creates an HTTPRoute to a shared listener.

The platform Gateway rejects attachment from an unapproved route namespace. Creating an object does not grant access.

DENYA workload calls the MCP Service directly.

Enforced backend network controls and backend authentication prevent bypass of the approved gateway path.

Two routes do not isolate two agents sharing credentials

If Agent A and Agent B share a namespace, process, or usable credential, separate HTTPRoutes do not establish separate authority. For mutually isolated agents, use separately enforced identities and runtime boundaries, often separate namespaces. A namespace alone also does not provide dedicated compute isolation.

Write operations require a separate permission path. In our workflow model, agents submit constrained workflow requests, and the approved workflow executor holds the resource-changing permissions.
