03 / Evidence behind the number
A small, explainable rulebook.
TierWhat it means in the proposed policy
100An explicitly declared critical controller wants replicas but currently has none available, with current generation observed.
90A verified availability deficit: Deployment Available=False for ≥ 5 minutes, or Pod Ready=False for ≥ 5 minutes with a blocking state such as CrashLoopBackOff.
80Zero-ready controller past its 10-minute startup grace; Pending/Unschedulable ≥ 10 minutes; at least 20 recognized application errors in inspected recent logs; or a recent terminal Job failure.
60Recent warning or OOM evidence without current impact. Context only at the default threshold.
The log rule counts observed error records, not a whole-namespace error rate. Missing timestamps cannot establish duration. Completed Jobs, scaled-to-zero workloads and ordinary rollouts retaining availability do not become active faults.




04 / If a message arrives twice
One accepted receipt per hourly slot.
A retry can reach Kafka twice. The receiver uses a trusted slot identity and a digest of the material findings.
Small ConfigMap receipts retain deduplication state for 72 hours; messages older than 2 hours are rejected. Quiet and unknown reports do not claim an investigation slot. Duplicate deliveries may start lightweight workflows, but must not create a second accepted receipt. Cross-hour incident cooldown comes later.


05 / What we actually build
A deliberately small footprint.
New components
One Python image, reused by the hourly assessor and receipt workflow. A CronJob, bounded report contract, trial Kafka topic and isolated Argo EventSource / Sensor / receipt workflow.
Read-only Kubernetes permissions for the assessor; tightly scoped receipt writes for the receiver.
Existing foundations
Kubernetes, Kafka and Argo. Keep the existing telemetry route intact. Verify the receiver’s namespace and EventBus compatibility before wiring it.
No new HTTP intake, PostgreSQL, broker, persistent worker or runtime LLM.
Measured operating budget
Hourly schedule. 120-second process budget. At most 60 API requests and 24 log reads, bounded to 3 MiB of logs. Report ≤ 8 KiB.
Trial: 5 namespaces / 100 running pods. Twenty report-only runs measured p95 2.804 seconds and up to 18 completed log reads per run.
The first milestone stops at an Argo receipt.
We prove that a real finding travels from the cluster through Kafka into Argo with correct replay handling. Model calls, tickets and remediation are separate follow-on capabilities. Reports carry automation_allowed: false.




06 / Evidence stages
The path from build to workplace proof.
  1. Bring up the home lab
    The older Proxmox cluster was Kubernetes 1.31.14. A disposable kind 1.35 cluster hosts the scheduled-timestamp proof.
  2. Implement the bounded job
    Implemented typed reports, deterministic rules and bounded reads in a pinned Python image. Seventeen behavior tests pass.
  3. Run isolated cluster fixtures
    Report-only runs measured runtime, memory and six-hour sample rotation across 100 running fixture Pods.
  4. Prove Kafka → Argo
    Canary reports reached Kafka and Argo. Receipts accepted first findings, suppressed replay and rejected conflicts; broker-down delivery failed boundedly.
  5. Observe real hourly runs
    The CronJob and independent monitor are running. Three real scheduled occurrences and an unaccelerated freshness deadline remain to be measured.
  6. Package for work
    The work bundle contains source, image inventory, manifests, tests, evidence and rollback instructions. Workplace wiring needs its own canary.


07 / The honest limits
Useful health assessment, with a defined scope.
Sampling has blind spots
Half the log budget rotates across workloads; half targets affected workloads. Brief incidents between runs can be missed. A quiet report means no breach observed in the declared checks, not complete cluster health.
Coverage is part of the result
Required reads failing means unknown unless positive findings already justify investigation. A known failure plus missing data still routes to Argo and also needs a coverage alert. Planned rotation alone is not a failure.
Delivery is bounded
There is no lossless outbox. An outage can lose a slot; the next run makes a fresh assessment. An independent Kafka consumer must detect missing reports. Urgent paging remains separate.
