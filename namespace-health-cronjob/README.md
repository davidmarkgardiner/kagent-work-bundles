# Scheduled namespace health assessment

Status: **the October 7 all-status build was exercised in an isolated Kubernetes home lab; selective Kafka admission is now implemented in source but has not been rebuilt or exercised live; workplace two-namespace pilot prepared but not deployed**.

An hourly Python CronJob reads Kubernetes workload state, recent Events and bounded recent Pod logs. It applies deterministic namespace rules and now publishes a report (at most 8 KiB) to Kafka only when one or more namespaces qualify for investigation. Quiet runs stay in Job logs; incomplete required coverage without a positive finding fails the Job. The Argo receiver validates investigation reports and records a first receipt for each slot. The initial receiver performs no model call, ticket update or remediation. [The admission and payload contract](TRIAGE-PAYLOAD-AND-ADMISSION.md) explains the fields and the monitoring change required by quiet suppression.

Start with [the step-by-step work-agent walkthrough](WORK-AGENT-WALKTHROUGH.md), [the short handoff](WORK-AGENT-START-HERE.md), [the build and test record](BUILD-AND-TEST.md) and [the workplace transfer details](WORKPLACE-HANDOFF.md). [The interactive HTML walkthrough](how-it-works.html) explains the decision flow with illustrative fixtures; it is not a live dashboard. [PLAN.md](PLAN.md) is the approved revision-3 design before selective admission. Opus and Kimi independently reviewed revision 2 with conditions, which [the resolution](REVIEW-RESOLUTION.md) incorporates; revision 3 and the later admission change were not independently rereviewed. The original responses and hashes remain under [reviews/](reviews/).

This route is independent of Alloy and Vector. It needs one custom Python image plus existing Kubernetes, Kafka and Argo. It does not need an HTTP intake, PostgreSQL, a new workplace broker, an always-running collector, or a runtime LLM. It assesses declared namespace checks rather than certifying complete cluster health or reconstructing a historical log stream.

## Evidence boundary

The isolated `kind-namespace-health` cluster used Kubernetes 1.35, Argo Events 1.9.11, Argo Workflows 4.0.8 and disposable Kafka 3.9.1. Seventeen behavior tests and two workplace-renderer tests pass. Live canary reports were produced and consumed with exact JSON and Kafka offsets; Argo accepted, deduplicated and rejected a conflicting slot as designed. A live partial-API fault retained known critical findings while marking coverage incomplete. Quiet and unknown reports started no investigation workflow. The external direct Kafka monitor delivered coverage, conflict, accelerated missing-slot and unreachable-broker alerts to a test webhook. Twenty runs over 100 running fixture Pods had p95 2.804 seconds, a maximum 60 API calls and 36,084 KiB peak process RSS. See [the image inventory](evidence/IMAGE-INVENTORY.json) for source, dependency, image and staging-archive hashes.

The real hourly CronJob is unsuspended, with an independent scheduled-topic receiver and external monitor. Its 13:00 UTC run delivered an investigate report and accepted Argo receipt; the monitor also delivered a genuine coverage alert when pagination caused the 100-Pod rotation to exceed its six-hour ceiling. A bounded pagination change then passed accelerated controller-created investigate, quiet and log-only transitions; the hourly schedule was restored. [The scheduled evidence](evidence/SCHEDULED-RUNS.json) separates those runs. [The monitor's later persisted state](evidence/HOURLY-SOAK-MONITOR.json) records valid Kafka reports at 14:00, 15:00, 16:00 and 17:00 UTC, all quiet. Exact broker replay and Argo inspection for those later hours remain unverified because runtime access was denied in the follow-up session; the unaccelerated missing-slot deadline also remains untested. The older Proxmox lab cluster is Kubernetes 1.31.14, below the scheduled-timestamp requirement, so it was not used for this proof. No workplace Kafka, CNI or application format is certified by the home-lab fixtures.

The public-safe base scan covers the entire bundle. The strict scan uses [a narrow allowlist](scan.allowlist) for executable Kubernetes token-handling syntax, a Kubernetes Secret mount, and exact disposable kind-namespace UIDs preserved in live JSON evidence. Those files still receive the base scan. No credentials, private endpoints or workplace identifiers belong in this bundle.
