# Sentinel workplace verification prompt

Copy the prompt below to the work agent. Fill in the target repository, cluster and application if they are already known.

> Audit the workplace implementation of the scheduled Sentinel probe for `{{TARGET_REPO}}`, `{{TARGET_CLUSTER}}` and `{{DEMO_APPLICATION}}`. Start by finding the authoritative manifests, deployed version and owner-approved policy. Verify the actual GitOps revision and live target. Treat the public demo, lab fixtures and screenshots as supporting context.
>
> Mark each row **PASS**, **FAIL**, **NOT VERIFIED** or **N/A** with a reason. Give a dated, redacted receipt or a precise source reference for each result. A PASS for runtime behaviour requires target-runtime evidence. Use read-only inspection and existing receipts first. Run an isolated canary only with existing approval. Keep test writes in an approved test destination. Leave production schedules, credentials and routing unchanged.
>
> 1. **Onboarding.** Trace the reviewed GitOps change through Flux or Sync and KRO to the generated workload-scoped scanner Job. Record the reconciled revision, registration and Job identities, image digest, schedule and effective permissions. Check who can create instances and who owns the image and schedule.
> 2. **Scanner behaviour.** Verify a healthy run and a persistent app failure. Check that generic critical signals and any enabled specialist checks run alongside each other. Confirm unknown or incomplete data remains visible. Exercise transient noise, approved suppression and deduplication of overlapping findings using approved evidence.
> 3. **Gateway and agent.** Correlate the worker report, authenticated Agent Gateway receipt, and agent investigation back into the correct cluster and namespace. Confirm the agent applies the intended access boundary and returns actionable evidence. Record the correlated identifiers and a denied-scope check.
> 4. **Alert budget and output.** Verify a maximum of three escalations per application per cluster in the configured daily window, including a fourth qualifying event, duplicate replay and independent scope for a second cluster. Confirm completions continue after the cap. Verify the configured opt-in route through receiving-system read-back. For GitLab, include issue, project, label and assignee where required. For ServiceNow or an approved endpoint, include the receiving record or delivery receipt. Check opt-out and replay produce no duplicate.
> 5. **Silent probe and recovery.** Confirm the central inventory includes active registrations before their first report. Show that an overdue first or recurring report triggers a single investigation. Check KRO reconciliation, Job state and Gateway receipt, and identify the operational owner. Verify paused registrations and receiver outages are handled separately, and an accepted recovery receipt closes the investigation.
>
> Return a Markdown table with **Check | Result | Environment and revision | Evidence | Gap or next action**. Include the target and audit time, summarize which checks need a test window or owner decision, and link to private receipts inside the workplace. Keep raw logs, credentials and internal endpoints out of any public copy.
