02 · The starting point

The previous MCP already had safeguards.

The primary PostgreSQL reference uses typed, read-only tools over approved views. It does not expose general CRUD operations.

Database-backed MCP

What it does

The agent calls tools such as get_namespace_count or get_namespace_summary. The adapter executes fixed, parameterized SQL against an approved PostgreSQL view.

Database access and password or Entra identity handling live in the MCP adapter.

Controls already present

  • Read-only transactions and least-privilege database grants.
  • Default limit of 50 rows and 32 KiB of result data.
  • Per-cell limits, a five-second statement timeout, and explicit truncation.
  • No arbitrary SQL tool in the primary typed-tool design.

“CRUD SQL MCP” is shorthand here. A separate legacy SQL-text route exists in the reference material, but the deployed workplace toolset must be inspected before comparing permissions or risk.

04 · A request end to end

Return evidence the model can cite.

1. Ask for a bounded graph

get_graph_context(
  query="production compliance relationships",
  context_size=10
)

The adapter currently sends POST JSON with query and context_size. The work agent must map a different private contract explicitly.

2. Retrieve from one fixed URL

The suspected workplace path is /get_context/get_context. Confirm the exact method, prefix and trailing slash in Swagger first.

3. Validate before returning to MCP

  • Strict response schema and expected source ID.
  • Entities plus views within the requested 1–10 object limit.
  • At most 20 directed relationships, with both endpoints in the returned graph.
  • A five-second HTTP deadline and 32 KiB upstream body limit.
  • A 64 KiB MCP result-envelope budget with a reserved request-ID allowance.

4. The agent answers from the returned source, scope, relationships and limitations. Partial results must say they are partial. An error or missing relationship is not evidence of compliance or absence.

Source IDs check routing consistency; they do not prove that the data is true.Adapter implementation
05 · Context with relationships

Make the evidence path explicit.

A context response can carry the connection between a workload, an assessment and a policy alongside the relevant facts.

Possible benefit

A service can resolve these relationships once, consistently, so an agent has less need to discover table joins or infer links from names.

The condition

The API must return correct, relevant edges with honest scope and coverage. Typed SQL can return the same relationships. REST alone does not create them.

07 · Benefits to evaluate

The potential gain is a better data contract.

Shared business meaning

One service can apply approved definitions, scope and retrieval rules for every caller.

Requires an owned contract and tests that catch semantic changes.

Less database coupling in MCP

The adapter can rely on an API rather than database drivers, grants and schema details.

Moves backend identity and query ownership into the service. That responsibility still exists.

More useful evidence per call

Relevant entities and explicit relationships may reduce exploratory tool calls or inferred joins.

Requires selective retrieval that returns the right context for the question.

Reusable integration

The same documented operation can serve agents, dashboards and other approved applications.

Requires stable versions, service reliability and a compatible mapping.

Smaller model context, fewer wrong answers and lower operating effort are hypotheses to measure. A REST response can be larger or less useful than a well-designed SQL result.

08 · What the API boundary does not solve

Keep the controls and account for another service.

Another failure point

The extra HTTP hop adds latency, availability and TLS dependencies. Contract changes can break the mapper.

Keep bounded deadlines, categorized errors, a rollback image and target-runtime canaries.

Data quality still matters

Stale context, wrong edges, incomplete scope and misleading human text can produce wrong answers.

Validate graph closure and coverage. Treat returned text as untrusted data, never instructions.

No auth needs confirmation

The adapter sends no Authorization header when its token-file setting is absent. That does not make the data public.

Confirm service access policy, verified HTTPS, approved callers and enforcing network controls.

Swagger is documentation. It does not prove read-only semantics, authorize data access or secure the endpoint. The suspected operation, its auth requirements and its response shape remain work-side gates.

No caller-supplied URLs, headers, SQL or write toolsWorkplace acceptance gates

Flat tables used 17.47% fewer input tokens in that replay. Both retained the relationships. This was not a REST-versus-SQL comparison and excluded orchestration, Gateway and retrieval tokens.

The useful workplace comparison

  • Use equivalent approved questions, data scopes and the same model.
  • Score correct facts, supporting edges, source, scope and partial-result warnings.
  • Measure complete MCP response bytes and per-call plus cumulative model tokens.
  • Count tool calls, latency, failures and human corrections.
  • Compare the existing typed SQL path with the mapped REST path, then decide by question type.

Include aggregates and exact lookups as well as topology questions. An API should not replace SQL operations that it cannot answer correctly.

  1. Confirm the Swagger operationCheck the actual method, path, request/response schema, read-only semantics, auth and data-owner scope.
  2. Make the smallest reviewed mappingPreserve the typed tool, fixed route, TLS checks, limits, provenance and existing workplace wiring.
  3. Build and prove on the targetUse an internal digest. Validate direct MCP calls, target kagent compatibility and grounded native answers.
  4. Measure and choose by use caseKeep exact SQL operations where they fit. Adopt REST context where equivalent tests show useful evidence and acceptable cost.
