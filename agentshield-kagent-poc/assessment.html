A useful source of security evidence for our AI SRE system. Start with a disposable detection proof, then connect findings to native kagent and our reviewed delivery flow.

Recommendation. Proceed with a bounded lab PoC. AgentShield can connect workload, identity, policy, and traffic evidence. Its current integration gaps and security model make a read-only deployment the right first step.

The resources are the protection boundary

AgentShield collects infrastructure observations, joins them into a versioned graph, detects changes, investigates selected signals with a model, and proposes remediations. That graph helps answer whether a workload acquired a new route to a sensitive service, which policies govern it, and what evidence supports the finding. An observed path or declared policy is not a complete proof of effective reachability or enforcement.

In our design, kagent remains the investigator and coordinator. Agentgateway continues to control model, MCP, and A2A traffic. Kubernetes RBAC, network controls, Kyverno, and workload identity continue to enforce permissions. AgentShield adds correlated evidence about those resources. It requires no kagent runtime plugin for its initial Kubernetes inventory.

Dashed observation lines represent configuration discovery. They do not claim live agentgateway traffic ingestion. The findings adapter is proposed work.

A lab deployment in two steps

1. Prove the product in isolation

Use a disposable kind cluster on a capacity-checked Proxmox executor. The upstream eval stack installs its own Cilium, Istio ambient, agentgateway, collector, database, and fixtures. Keep it separate from the native kagent cluster. Prefer another VM if host resources are tight.

Begin with detector-only evals. This avoids model costs while proving sensor observations and deterministic rules. The browser playground is useful for learning the UI, but uses a fake backend and proves no cluster behavior.

2. Observe native kagent alpha17

Read the native access guide, verify the executor and SSH trust, and run the pinned native preflight before installing anything. Inventory CNI, network policy enforcement, Gateway API versions, GatewayClass controller, CRDs, model protocol, and node capacity.

Deploy only the AgentShield observer, its dedicated database, and access controls. Do not replace the native cluster's CNI, install the full eval stack into it, or reuse kagent's database.

The proposed graph-only Helm configuration

Provision a dedicated PostgreSQL 16 database and role first. It needs DDL privileges for startup migrations. Use TLS for network connections. Supply its URL through the approved secret mechanism as agentshield-database, key url. One process owns one database. Keep replicaCount: 1.

image:
  repository: agentshield
  tag: poc-b179824
  pullPolicy: IfNotPresent
replicaCount: 1
database:
  existingSecret: agentshield-database
  secretKey: url
discovery:
  kubernetes:
    clusterID: lab-native-alpha17
    sourceID: kubernetes/lab-native-alpha17
  istio:
    clusterID: lab-native-alpha17
    sourceID: kubernetes/lab-native-alpha17
  agentgateway:
    clusterID: lab-native-alpha17
    sourceID: kubernetes/lab-native-alpha17
  cilium:
    clusterID: lab-native-alpha17
    sourceID: kubernetes/lab-native-alpha17
  falco:
    clusterID: lab-native-alpha17
    sourceID: kubernetes/lab-native-alpha17

Save this as lab-values.yaml. It deliberately leaves both model features off. Matching cluster and source IDs let plugin evidence join onto the same objects. These IDs must remain stable for the database lifetime.

kubectl --context kind-kagent-alpha17 get nodes
kubectl --context kind-kagent-alpha17 -n kagent \
  get deployment kagent-controller -o jsonpath='{.spec.template.spec.containers[*].image}'

helm template agentshield deploy/kubernetes \
  --namespace agentshield-system -f lab-values.yaml > rendered.yaml

Before apply, verify the exact controller version, create a restricted Pod Security namespace, install reviewed API access controls, and provide the database Secret. Restrict the unauthenticated service with an enforcing CNI and/or authenticated proxy. NetworkPolicy objects alone do not protect a cluster whose CNI ignores them.

helm upgrade --install agentshield deploy/kubernetes \
  --kube-context kind-kagent-alpha17 \
  --namespace agentshield-system -f lab-values.yaml
kubectl --context kind-kagent-alpha17 -n agentshield-system \
  rollout status deployment/agentshield-agentshield
kubectl --context kind-kagent-alpha17 -n agentshield-system \
  port-forward --address 127.0.0.1 service/agentshield-agentshield 8088:8088

From the executor's local tunnel, open http://127.0.0.1:8088. An SSH local forward is needed to view an executor-local port from the Mac. Keep the service internal. Port forwarding does not make its in-cluster listener loopback, so it does not enable live remediation.

Enable investigation only after the inventory proof

The chart has no extraArgs or feature values for this. Use a reviewed chart patch or Flux post-renderer to add the required environment settings or arguments. Configure AGENTSHIELD_AGENTIC_INVESTIGATION=true, an approved model endpoint and model, and a Secret-backed key. Leave rule authoring off initially. Set an explicit investigation budget, for example --agentic-investigation-max-per-hour=12, plus gateway token and cost limits. That is a proposed cap on investigations, not on individual model requests.

The client appends /v1/responses to --model-endpoint. Use a base URL that resolves to that exact route. Our existing chat-completions path is not sufficient proof. Test the full tool-use and structured-answer round trip, not just an HTTP 200. No model request is authorized or made in this investigation.

Proofs that answer separate questions

Each phase has an explicit result. A screenshot, healthy Pod, or accepted telemetry request does not establish detection or enforcement.

Upstream commands for the disposable test cluster

AGENTSHIELD_EVAL_DETECTOR_ONLY=1 make eval-up
AGENTSHIELD_EVAL_DETECTOR_ONLY=1 make eval-run
AGENTSHIELD_EVAL_DETECTOR_ONLY=1 make eval-rules

These commands create a multi-component cluster. Check capacity and inspect the installer first. Do not point them at the existing native cluster. The full model lane uses make eval-up, make eval-check, and make eval-run with an approved key and budget. The suite includes model authoring, so enabling it can start additional paid calls. Teardown uses make eval-down after preserving evidence.

Use dummy services and fabricated credentials. Pair suspicious behavior with legitimate rotation, repository inventory, and routine rollouts. Start with all upstream cases, then add cases specific to our agent-to-MCP and agent-to-Argo boundaries. The upstream suite is a smoke test, not a published detection-accuracy benchmark.

Capture UTC timestamps, source and image hashes, cluster versions, manifest revision, resource UIDs, rule versions, graph evidence, allow/deny probes, model usage, specialist output, and rollback receipts. Proposed promotion gates are all selected attack and benign expectations passing, no observer write permissions, no unauthenticated access from an unapproved Pod, and no mutation before recorded external approval. Repeat model cases to show variation.

The smallest integration to build after the product proof

A scheduled poller can read GET /api/v1/findings and the per-finding endpoint. The proposed adapter exposes fixed read-only operations such as list_security_findings, get_security_finding, and get_security_evidence. Limit response rows, bytes, cell length, and time. Carry finding ID, cluster, graph revision, affected resource identities, evidence IDs, status, timestamp, and truncation metadata. Keep the complete graph outside the model context.

Use stable workload identities and finding IDs for deduplication. Do not use literal Pod names alone. Cursor handling belongs in a bounded worker, not an agent that auto-pages through the full graph. Polling is a proposed integration; this checkout has a findings HTTP API, not an identified native Argo event publisher.

The supplied agentshield-reasoning-mcp binary is another PoC option. It serves an immutable saved packet, optionally with pinned telemetry context. It is not a continuously refreshed graph MCP server. It has no built-in authentication. Put it behind approved authenticated infrastructure before giving kagent remote access, and explicitly manage packet freshness.

Where the workplace PoC must stop short

Do not claim full Azure identity or network-path coverage from the Kubernetes plugin. Do not equate an HTTPRoute backend with caller authorization. Do not equate a stored NetworkPolicy with an enforced deny. Do not let the specialist call AgentShield's approval endpoints. Keep the observer read-only, and let a narrowly scoped workflow identity execute only an approved change.

The unauthenticated API, cluster-wide Secret read access, model data disclosure, non-durable approval identities, and incomplete telemetry transports are concrete adoption constraints. A dedicated lower-environment cluster is a better first workplace target than a shared cluster containing real secrets. An API proxy alone does not solve collector privileges or stored sensitive payloads.
