# Deliver a verified agent and a rehearsed demo

Delivery means the selected target implementation works, its security controls have fresh evidence, and another person can repeat the demonstration. The work agent continues through implementation, diagnosis, fixes, verification, and rehearsal. A plan, rendered manifests, green source tests, or Ready flags alone do not complete delivery.

The existing HostedAgent operator is the work starting point. Preserve its four CRDs, compatible images, current profiles and working no-Substrate path. The separate native lab adapter and its receipts remain reference evidence. They are not the completed work implementation.

## Required outcomes

| Gate | Desired state | Evidence required |
| --- | --- | --- |
| D01 | Existing operator extended through a new protected profile, with old behavior preserved | Reviewed file/resource delta, existing regressions, actual request/child ownership and version records |
| D02 | An owner applies one small approved YAML file and the composer prepares all dedicated resources | Final owner YAML, generated inventory, exact routes/grants/policies, shared-versus-owned boundary |
| D03 | A fresh invocation loads the reviewed skill and knowledge, uses the approved model, and obtains the approved MCP result | Current task or Job identity, actual tool calls/results, content pins and backend witness |
| D04 | Unauthorized callers, tools, bindings and unsafe workloads are denied | Real admission and runtime denials, admitted controls, wrong-identity tests and unchanged forbidden backend counters |
| D05 | Direct paths cannot bypass the approved boundary | Effective policy set and actual consumer traffic probes, paired with a reachable approved path; actual actor proof for native claims |
| D06 | Expiry, revocation and partial failure fail closed; normal retirement and recreation are safe | Fresh lifecycle receipts, in-flight settlement bound, no new authority after revocation, old UID approval denied, shared resources retained |
| D07 | The selected target can build and run from approved internal inputs | Artifact ledger, internal digests, cold consumer retrieval, offline build evidence and credential references without values |
| D08 | A presenter can repeat a truthful live demonstration of the delivered revision | Successful full rehearsal, timed run sheet, current scope/identity, receipt index, fallback and reset instructions |
| D09 | The receiving engineer can operate and repeat the result | Completed human sheet, changed files, exact commands, final YAML, private receipt locations, comparison, limits, rollback and resume record |

Apply these gates to the selected authorized path. A standalone Job is not native kagent/Harness execution and cannot satisfy an actor-isolation claim. If native prerequisites are absent, finish independent work on the existing path and record the native/KRO comparison as blocked. Do not mark a native comparison complete, invent a winner, or install Substrate to bypass the scope decision.

Entra, credential renewal, live ephemeral-container admission, capacity budgets and any other selected exposure requirements remain applicable target gates. A scope exclusion must be explicit in the report and demonstration. An unknown, skipped or blocked required gate is not a pass.

## Keep going until those outcomes are verified

1. Inventory the existing target and match each human prerequisite to an owner and evidence. Reuse compatible work before proposing builds or changes.
2. Implement the smallest reviewed delta within the existing authorization. Render and inspect it, then use the approved target delivery process.
3. Run the relevant source, schema, admission, functional, authorization, network and lifecycle checks. Capture exact commands, identities, source revision, failures and results in private evidence.
4. Fix each concrete failure and rerun the affected gate. Preserve failed receipts. Broaden tests when the fix changes a shared boundary. Do not weaken assertions, substitute fixtures, or relabel historical evidence.
5. Run the full presenter rehearsal against the final delivered revision. Reapprove recreated objects through the independent publisher and repeat acceptance when their identities change. Leave the demo in its agreed stable state.
6. Complete the outcome report and handoff only after the required gates pass. Use [the demo run sheet](SHOWCASE-DEMO.md) and [report template](examples/delivery-report.example.json).

Continue without repeated permission prompts for actions already covered by the supplied authorization. Missing external inputs, unavailable authority, provider quota/access failures, or a new change outside that scope are real blockers. Record the exact blocker, owner and required action, then continue independent work. Do not spin, repeatedly retry a denied provider, bypass a gate, or claim completion because the remaining work is blocked.

If the agent must hand over or its session ends, save `WORK-STATE.md` and an evidence index in the private work directory. Record the current revision, actual runtime path, completed/failed/blocked gates, changed resource identities, last commands, recovery state and next executable action. Resume from that checkpoint. A checkpoint is progress, not delivered success.

## Final outcome report

Use one of `verified-demo-ready`, `in-progress`, or `blocked`. Use `verified-demo-ready` only when every required gate has a fresh pass and the full rehearsal has succeeded. Record non-applicable gates with their scope decision. The report must identify which operator/profile was actually implemented, what was reused, which work environment was tested, and what remains unproved.

HTML checkboxes, presentation slides, PDF pages and manually entered status fields are supporting documents. They do not verify the target and must not be used as live telemetry.
