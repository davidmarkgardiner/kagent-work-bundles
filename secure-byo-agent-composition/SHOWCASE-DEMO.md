# Rehearse the delivered agent

This is the work agent's rehearsal contract. It is not a claim that the workplace demonstration has already run. Use a dedicated authorized POC scope and the final delivered revision. Follow [the desired state](DESIRED-STATE.md); preserve the existing HostedAgent operator and distinguish standalone from native execution.

## Prepare the demonstration

Record the source revision, target context, profile, namespace, current request/Agent or Job identities, approved caller, capability, and receipt directory privately. Confirm model availability, current approval, credential lifetime, policy attachment and network enforcement. Prepare a fresh immutable request or the reviewed reset procedure. Never put live tokens on screen.

The presenter needs the final one-file owner YAML, an inventory view, a fresh functional receipt, admitted and denied specimens, call-time revocation controls, the comparison, and safe reset instructions. Adapt the lab helpers to the actual existing operator API, names and selected runtime first. Do not run a helper expecting HostedSecureAgent against HostedAgent without that adaptation.

## Run the 8 to 12 minute story

| Step | Show | Proof to retain |
| --- | --- | --- |
| 1. Explain the boundary | Existing operator or approved KRO profile, runtime path, owner authority and platform prerequisites | Exact revision/profile and a clear list of shared versus dedicated resources |
| 2. Apply one request | Submit the reviewed owner YAML under the restricted owner identity | Actual accepted request and the generated resource graph, routes and grants |
| 3. Use the agent | Invoke with the approved identity and supplied synthetic documentation case | Fresh task or completed Job, actual skill/knowledge calls, approved model and MCP result, current content pins |
| 4. Reject unsafe changes | Present an admitted control, then forbidden binding/privilege and copied-identity cases | Actual policy/rule denial and a matching allowed control; no schema-only or RBAC-only failure presented as Kyverno proof |
| 5. Deny the wrong caller and direct path | Wrong principal or audience, forbidden operation and bypass attempts | Actual denial plus backend witness; reachable approved path as a positive control |
| 6. Revoke and recover | Revoke current approval, deny fresh authority, explain already-dispatched work, then independently restore approval | Timestamped counters, no returned protected result, observed settlement bound and fresh successful recovery |
| 7. Retire and recreate | Remove the dedicated request, retain shared prerequisites, and reject stale same-name approval | Complete owned inventory cleanup and new UIDs; fresh approval and fresh acceptance after recreation |
| 8. Compare and close | Explain KRO versus the existing HostedAgent extension and leave the agreed stable state | Rehearsal receipt, exact tested scope, limits, and operator handoff |

For a standalone-only target, show the actual completed Job and its receipt. Do not present it as a native Agent/Harness, sandbox actor or native KRO comparison. Mark unavailable comparison gates blocked. A demonstration of fewer components must state that scope.

The MCP status is synthetic read-only evidence, not an Azure investigation or remediation. HTML/PDF support is explanatory. Do not animate status, show fabricated live counts, or call a saved receipt a fresh run.

## Recover from a failed rehearsal

Keep the failed receipt and diagnose the exact failing gate. Repair the underlying cause, rerun affected checks, then repeat the complete rehearsal for the final revision. A recorded historical walkthrough may be shown only if clearly labelled historical; it does not pass the live delivery gate.

Follow [recovery](docs/RECOVERY.md) and the target's adapted operator retirement procedure. Do not force-remove finalizers, adopt foreign objects, widen network grants, disable Kyverno or replace provider data with fixtures. Leave no temporary outage harness or diagnostic privilege behind.

## Rehearsal receipt

Record date/time, presenter, revision, target path, exact run commands, gate IDs, current resource identities, functional and negative receipt paths, observed timing bounds, reset outcome, final state and remaining gaps. Store target details privately and reference them from the delivery report. The work agent may report `verified-demo-ready` only after this full rehearsal succeeds and every required target gate passes.
