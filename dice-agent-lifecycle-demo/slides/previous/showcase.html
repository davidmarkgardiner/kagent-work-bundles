Story 1 · Build, deploy, and consume · 02 / 08

A small request becomes an agent API.

KRO, the Kube Resource Orchestrator, assembles the resources. Native kagent runs the agent. The platform owns credentials and the security configuration.

1. DefineDrop in frontend YAML or choose a prompt, skills and tools.
→
2. DeliverReview the YAML through the team's GitOps process.
→
3. AssembleKRO creates the Agent, identities, policies, routes, and verification Job.
→
4. VerifyGolden tests the model path before KRO creates the caller route.
→
5. Receive your APIThe dashboard returns the protected endpoint and its allowed caller contract.

What the team supplies

The classic request has four spec fields. Catalog choices resolve to reviewed native configuration and explicit tool names.

apiVersion: demo.kagent.dev/v1alpha1
kind: ClassicSecureAgent
metadata:
  name: demo
  namespace: classic-agents
spec:
  modelConfig: approved-model
  systemPrompt: Reply accurately and concisely. Use only the approved tools when asked.
  skills: []
  tools: []

What the team receives

  • A native Agent and generated runtime Service in its allocated namespace.
  • A protected invocation route and an AgentCard describing the A2A interface.
  • Approved model and tool bindings, with platform-owned credentials.
  • A versioned definition and verification evidence that operators can inspect.

The API returned to the user

http://{{GATEWAY_SERVICE_DNS}}:8080/classic/classic-agents/demo/invoke

Current JWT subject system:serviceaccount:classic-agents:demo-caller, audience secure-agent-classic. The trusted issuer supplies the token at runtime.

Try the mock IDP: YAML or form → Send → API handoff

An application can add a VirtualService or another API layer where needed. It must preserve the authenticated Gateway path and caller permissions.

The checked lab supports one bounded classic-agents/demo slot. The mock IDP is a local simulation. Location and custom IAM / Entra identity are planned request metadata; today's graph does not apply them. Repeated team onboarding and arbitrary namespace provisioning remain the product direction.

Story 1 · Current security composition · 03 / 08

Routes select the agent. JWT policy admits the caller.

The current classic demo uses Kubernetes service-account JWTs, separate verifier and caller identities, and protected Agent Gateway routes.

Caller identityShort-lived JWT with the expected issuer, audience, and subject.
→
Gateway listenerPlatform chooses which namespaces can attach routes.
→
HTTPRoute + policyMatch the invocation path. Require a valid JWT and the exact permitted caller.
→
Agent ServiceForward the accepted request to the native A2A endpoint.

HTTPRoute

Selects the path and backend. Attached JWT validation checks the token. Authorization checks the permitted identity.

The caller route is created only after Golden succeeds. A completed verification Job is a dated check, not a continuous revocation service.

ReferenceGrant

The backend owner permits a specified route namespace to reference its Service across namespaces.

The current classic layout needs no grant because its route and backend share a namespace. Shared layouts may need one. Gateway attachment uses allowedRoutes.

A grant does not authenticate a request.

Controls underneath

Separate ServiceAccounts, narrow RBAC, restricted runtime settings, approved tools, and NetworkPolicy intent constrain the workload.

Customers manage the request, while the platform owns child policies and credentials. Direct-Service and controller bypass tests must be verified on the receiving cluster.

Recorded on 4 November: model and caller PONG passed. Missing caller JWT returned 401. A verifier identity on the caller route returned 403.

Strict JWT validation and caller authorization

# KRO template from spec.resources. CEL is resolved by KRO.
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: ${schema.metadata.name}-invoke
  namespace: ${schema.metadata.namespace}
spec:
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: ${schema.metadata.name}-invoke
  traffic:
    jwtAuthentication:
      mode: Strict
      preserveToken: false
      providers:
      - issuer: '{{KUBERNETES_SERVICE_ACCOUNT_ISSUER}}'
        audiences:
        - secure-agent-classic
        jwks:
          inline: '{{KUBERNETES_JWKS_JSON}}'
    authorization:
      action: Require
      policy:
        matchExpressions:
        - jwt.sub == "system:serviceaccount:classic-agents:${schema.metadata.name}-caller"

Story 1 · Next identity integration · 04 / 08

Entra adds organisational identity at each boundary.

Planned for this composition. Entra still issues tokens that the Gateway must validate and authorize. A user's permission to invoke an agent does not grant that agent access to a backend.

Planned · Incoming caller

Person or application → agent

Entra token → Gateway validation → invocation role → approved agent
  • Register the protected API and define its intended audience.
  • Validate the approved issuer, signature, audience, and expiry.
  • Authorize the intended user or application using the agreed claims and roles.
  • Keep verifier and caller identity contracts separate.
Planned · Outgoing workload

Agent or Gateway → MCP and model

ServiceAccount → federation → UAMI → resource-scoped access token
  • Bind the workload to its approved managed identity.
  • Acquire a token for the destination's audience where that backend supports Entra.
  • Grant only the required model or tool operations at the destination.
  • Use a separate, reviewed delegated flow if acting on behalf of the user is required.
Caller authentication, agent invocation permission, and backend permission are three separate checks.

What continues to apply

HTTPRoutes, conditional ReferenceGrants, NetworkPolicies, explicit tool lists, namespace RBAC, and versioned definitions still constrain access.

What proves the next iteration

One allowed caller and tool read, plus denials for wrong audience, expired token, unauthorized role, another agent's tools, and an unapproved operation. Check token renewal and the defined revocation behaviour.

Story 1 · Models, tools, cost, and visibility · 05 / 08

One governed connection to models and tools.

Agent Gateway is the shared policy and routing point. The model garden defines approved model choices. MCP adapters expose bounded operations on systems and data.

ApplicationCalls the permitted agent API.
→
Native agentUses its approved model and explicit tool list.
→
Agent GatewayRoutes, authorizes, limits, and records supported traffic.
→
Two backend familiesModel garden and provider APIs.
MCP tools and their protected resources.

Authenticate both families

Models. Authorize the calling workload for an approved model. The Gateway uses the provider's required credential, such as a managed identity or a platform-held API key.

MCP tools. Authenticate the agent at the tool boundary, allow named operations, and retain the adapter's own resource permissions. Backend credentials remain platform-owned.

Use OAuth or Entra where supported. Never forward a caller token to a destination with a different audience.

Control token use and cost

  1. Allow approved models and tool names. Keep prompts and tool responses bounded.
  2. Set output-token limits, request limits, concurrency, and deadlines.
  3. Apply team or identity token budgets. Global limits need shared accounting.
  4. Bound retries and specialist turns. Escalate only admitted incident evidence.
  5. Attribute actual input and output usage to team, agent, and model.

Usage-based token limits can account after completion. Pair them with generation limits. A token quota alone is not an exact currency cap.

Observe the complete request

Carry task, session, and available trace IDs through the agent, Gateway, model, and MCP call.

  • Metrics. Volume, input/output tokens, latency, errors, policy denials, and budget rejections.
  • Logs. Route and selected model, caller attribution, tool outcome, and policy decision. Redact credentials and sensitive content.
  • Traces. Correlate the hops through OTel and the existing LGTM collectors and backends.
Show a real request beside its policy result, tool receipt, token counters, and trace. The operator can then explain both the answer and its cost.

This is the shared-platform integration design. The checked SDLC rig sends models through Gateway and calls GitLab MCP directly. Gateway-mediated MCP authentication and telemetry remain a separate integration to prove. The classic PONG receipt proves neither cost controls nor an end-to-end trace.

Story 2 · We consume DICE for cluster reliability · 06 / 08

Three short iterations. Each builds on the last.

We started with LGTM observability, added evidence-first triage, then moved incident admission closer to the application.

01

Collect and inspect with LGTM

Application and Kubernetes signals → Alloy → LGTM → SRE dashboards and alerts

Alloy collects logs and events at source. Loki holds logs, Mimir holds metrics, Tempo holds traces where wired, and Grafana presents the evidence. SREs investigate the signals and decide what to do.

02

Add source-level health triage

Alloy → Vector → Kafka → Argo → read-only kagent → GitLab issue

Our health-triage capability gathers source evidence and sends bounded candidates through Kafka. The management-side agent investigates and creates an evidence-backed work item. LGTM continues to serve operators. Collection and transport do not require an LLM on every log line.

03

Admit important incidents beside the application

Application evidence → bounded model classifier → durable threshold gate → kagent specialist

An application-owned integration selects evidence. A classifier assesses the candidate; a durable gate checks the criticality and confidence threshold before dispatch. The specialist can prepare a remediation MR. Human approval and the controlled delivery path precede execution and recovery checks.

Use observability to see the problem, triage to explain it, and governed remediation to resolve an approved change.
Source distinctions for review

The application specialist runs alongside the application, not inside its binary. The inspected classifier uses Kimi with a 0.95 admission threshold; the hourly top-N selector is deterministic. “GEF” remains an unconfirmed name, so these sheets use “model classifier.” These are successive patterns, not a claim that every component is one live deployment.

Story 2 · We consume DICE for software delivery · 07 / 08

A labelled Kanban ticket becomes reviewable work.

A team assigns work to the agent workflow through its GitLab board. Specialist agents plan, build, test, and review within the task's permitted scope.

1. Select a ticketAcceptance criteria and approved agent labels.
→
2. IngestA listener or board poller admits eligible work.
→
3. DelegatePM coordinates builder, tester, and reviewer agents.
→
4. VerifyRead back commits, CI, draft MR, and review on the current head.
→
5. Human mergeA person reviews and accepts the delivery.
Inspected implementation

The GitLab board is the work queue.

The reference rig polls every two minutes for sdlc-rig-poc and agent:plan. It advances one checkpoint per run and uses a shared writer Lease.

Failed CI routes work to agent:changes. Three unsuccessful stage attempts route it to agent:blocked.

“Listener” describes the product entry point. The source-grounded rig here is a poller, rather than a claimed webhook execution.

Permissions follow the role.

GitLab MCP exposes named issue, branch, file, pipeline, draft-MR, and review-note operations. The agents receive no merge, delete, project-settings, or arbitrary GitLab API tool.

Model requests use Agent Gateway. GitLab remains the source of truth for artifacts and state. An agent saying “done” does not advance the workflow without the corresponding artifacts.

The same pattern can accept a bounded engineering task raised during SRE triage.

Teams use their existing board to assign bounded work. They receive a tested draft MR and evidence to support a human decision.

Story 2 · We consume DICE through one SRE conversation · 08 / 08

SRE Lens asks the right specialists.

An SRE talks to one orchestration agent. It chooses the permitted specialist agents, gathers evidence through their MCP tools, and returns one cited answer.

GitLab MCP

Find related tickets, changes, MRs, and pipeline status. Link the operational question to engineering work.

Kubernetes MCP

Read the permitted namespace and workload state, events, and configuration to corroborate the incident.

Data MCP

Read approved, bounded database or data-service results. Existing catalog material names Denodo; PostgreSQL has a separate typed, read-only adapter.

The “Node.js MCP” name in the brief awaits confirmation. Runtime language alone does not identify the data backend.

SNOW Agent · ServiceNow

Read incident status, assignment and timeline within the permitted record scope. Return incident references; any record change requires a separate approved workflow.

KB Agent · Vector retrieval

Find relevant knowledge articles through querydoc MCP and the article vector index. Return excerpts with source paths and version; missing or stale guidance stays explicit.

SRE Lens is also an API consumer of DICE. The same agent API can be embedded in another application or operational workflow.
