Who provides what for
AKS → agent → MCP?

Two separate token checks protect two different calls. Your caller UAMI gets permission to invoke the agent. The running agent's child Agent ID gets permission to use the MCP API. The connection between those calls is the agent workflow and our gateway configuration.

Answer to the central question: the Entra team does not connect your caller UAMI to the blueprint. The blueprint does not approve incoming application calls, and the agent does not ask the blueprint for a yes/no decision every time it calls MCP. Entra issues two different tokens; our two gateway routes check them.

Walk through one request

  1. Before the application calls: its AKS ServiceAccount has a FIC on the caller UAMI. The application presents its projected ServiceAccount token to Entra and asks for a token whose audience is the protected A2A API. Entra verifies the federation and includes the UAMI's assigned A2A app role in the issued token.
  2. The application calls the agent: it sends that A2A token to our agentgateway route. Our gateway checks issuer, signature, audience, expiry, role, and exact caller UAMI identity. If allowed, it forwards the request to the named kagent Agent. The blueprint is not consulted here.
  3. The agent decides it needs a tool: its own ServiceAccount, or its dedicated token proxy's ServiceAccount, has a FIC directly on the Agent ID blueprint application. That token holder uses the blueprint credential to ask Entra for a token representing the named child Agent ID, with the MCP API as audience. Entra includes the role inherited from the approved grant on the blueprint principal in the child token.
  4. The agent calls MCP: it sends the child Agent ID token to our MCP gateway route. Our gateway checks issuer, signature, audience, expiry, exact child identity, role, and MCP tool name. Only then does it forward the tool call to the MCP server. The MCP server may need its own separate identity for whatever it accesses behind the tool.

Where the two halves join: our A2A route targets the kagent Agent; that Agent is configured to use our MCP route. Entra stores the identities, federated credentials and API role assignments. It does not store an application-UAMI-to-blueprint link for this design.

What the blueprint actually is

Inbound A2A · no blueprint

Caller UAMI + protected A2A API

The UAMI is the caller's identity. The A2A API is the resource the caller wants to reach. Entra assigns an A2A application role to the UAMI; our A2A gateway route accepts only the right token and caller for this agent. Request 1 still needs the A2A API's application/client ID and audience, plus the UAMI's client and principal IDs. It needs no Agent ID blueprint.

Outbound MCP · blueprint

Parent grant + child identity

The blueprint holds the credential that lets a workload ask Entra for a token on behalf of a child Agent ID. An approved MCP API app-role grant on the blueprint principal flows to every current and future child of that blueprint. The child Agent ID appears in the token as the caller identity; our MCP gateway checks its exact ID, inherited role, and tool name. The blueprint is not a live permission checker on each MCP call.

Can one blueprint be reused? Yes, for children intended to share its inherited MCP API permission. Every present and future child of this blueprint inherits the approved grant, so its owner must control which children are created and review later grants. Our gateway separately registers each approved child identity and allowed tool. Sharing a blueprint also shares its credential boundary: someone able to use that credential may be able to obtain tokens for other children under it. Use a dedicated blueprint or a proven broker before sharing it across independent agents or teams.

Entra validates federation and assignments when it issues each token. Agentgateway validates the signed token and route policy when a call arrives. The application and agent use different tokens and audiences.

What the two requests ask for

Request 1 · caller → agent

Allow one AKS application to invoke one agent

We provide in the private request:

  • Environment, team, sponsor, calling application, target agent, and the approved A2A invoke role.
  • Caller UAMI client ID and principal/object ID, plus its resource name and resource group.
  • AKS cluster, exact OIDC issuer, caller namespace and ServiceAccount; the subject is system:serviceaccount:{{CALLER_NAMESPACE}}:{{CALLER_SERVICE_ACCOUNT}}.
  • Who owns the caller UAMI federated identity credential (FIC): us/platform if authorised, or Entra/AACM.

Entra/AACM does: create or identify the protected A2A API and service principal, define an Application app role, assign it to the caller UAMI principal, and return a read-back. If agreed, they also create the caller UAMI FIC for the exact AKS issuer and ServiceAccount subject.

Assignment mapping: principalId = caller UAMI object ID; resourceId = A2A API service-principal object ID; appRoleId = A2A invoke role ID.

Request 2 · agent → MCP

Let approved child agents inherit MCP API permission

We provide in the private request:

  • Environment, team, sponsor, agent name and namespace, protected MCP API, requested application role, and one permitted MCP tool.
  • AKS cluster and exact OIDC issuer again, plus the agent token holder's namespace and ServiceAccount. This may be the Agent Pod or a dedicated token proxy.
  • Exact subject system:serviceaccount:{{AGENT_NAMESPACE}}:{{AGENT_SERVICE_ACCOUNT}} and federation audience api://AzureADTokenExchange.

Entra/AACM does: approve or create a dedicated blueprint application and principal, create one runtime child Agent ID, place a FIC on the blueprint application for the agent token holder, create or identify the MCP API and its Application app role, declare that role in requiredResourceAccess, configure inheritablePermissions for roles but no delegated scopes, and grant the role to the blueprint principal.

Assignment mapping: principalId = blueprint principal object ID; resourceId = MCP API service-principal object ID; appRoleId = MCP role ID. All present and future children inherit the role. Our gateway still registers each approved child identity and tool.

What we ask the Entra team to return

For Request 1

A2A API app/client ID, API service-principal object ID, Application ID URI/token audience, invoke role value and ID, caller UAMI principal used in the assignment, assignment read-back, caller FIC owner and read-back if they create it, approver, and revocation path.

For Request 2

Blueprint app/client and object IDs, blueprint-principal object ID, child Agent ID app/client and object IDs, child-to-blueprint link, exact blueprint FIC read-back, MCP API app/client and service-principal IDs, MCP audience, role value and ID, inheritance declarations, blueprint-principal grant read-back, child inventory, sanitized fresh child-token role check, owner, approver, and revocation path.

Put real IDs, issuer URLs, ticket links and any live evidence only in the approved private work system. No credentials or access tokens are requested in the reply.

Three decisions to settle together

  1. Who owns the caller UAMI FIC? We can supply the caller UAMI and AKS facts; its FIC still needs an agreed creator and read-back.
  2. Which ServiceAccount obtains the child Agent ID token? Use the Agent Pod's ServiceAccount or a dedicated token proxy's ServiceAccount. The blueprint FIC must name that exact subject, and only the chosen token holder should access the blueprint credential.
  3. Who owns the A2A and MCP API registrations? Entra may create them or approve existing resource apps. Their audiences and app roles must be agreed with the platform and MCP owners before assignments are made.

Current evidence boundary: a disposable AKS pilot proved direct ServiceAccount → blueprint federation and A2A → Agent → MCP with negative tests. It used a direct child MCP grant, while Request 2 now requests blueprint inheritance; that change still needs a fresh child-token and gateway proof. It used a caller blueprint for its A2A positive test, while Request 1 asks for a caller UAMI. The pilot used a manual token update and Pod restart; automatic renewal, work-tenant AACM integration and production deployment remain to be proved. The earlier ServiceAccount → UAMI → blueprint chain failed and is not the Request 2 design.
