# ADR-0001: Govern agent, MCP and model access through Entra and Agent Gateway

Status: proposed for architecture review. Date: 11 November 2026. Decision owners: the receiving platform and identity owners. This record documents the requested target design. It authorizes no tenant, cluster, role, provider or production change.

## Context

Teams need an agent API that they can deploy through GitOps and consume with existing application identities. Skills live in GitLab. Agents and MCP tools run in Kubernetes and appear in a central registry. Model inference comes from the existing model garden and its approved LLM endpoints. Observability and evaluation must support the whole lifecycle.

The architecture needs to distinguish identity issuance, request routing, authorization, execution permission and quality assessment. A route, registry entry, skill mount or trace alone cannot establish all of them.

## Decision

1. Keep agents on the approved Kubernetes runtime. Use the existing Flux/KRO delivery contract, scoped profiles and current workload owners. Preserve shared platform services.
2. Use Entra-issued access tokens at protected API boundaries. Applications use an approved UAMI/service identity. Humans use an approved interactive client or authenticate to an application that performs its own authorization before its UAMI invokes an agent.
3. Make caller-to-agent and agent-to-MCP separate resource and permission checks. Use the selected Entra Agent ID credential adapter or approved per-agent workload identity for outgoing agent calls. The caller UAMI is not reused as the agent's identity by default.
4. Keep Agent Gateway on the approved agent, MCP and model paths. Validate the required principal, resource audience and permission; apply route/tool/model policy; restrict direct backend access. The MCP service retains a separate least-privilege backend identity.
5. Support either Istio-managed API authentication/authorization alongside the VirtualService, or application-managed Entra validation. Routing configuration alone does not secure the API. A middle-tier application obtains a token for the actual downstream resource.
6. Register agents, MCP services and skills with immutable release references, owners, intended connections and acceptance evidence. Translate approved connections into enforceable policy through GitOps. Registration does not grant access.
7. Publish reviewed GitLab skills through the platform's approved release mechanism and prove native use. Route inference through the existing model garden and selected LLM endpoints. This ADR does not replace the model garden or move agent hosting to a provider service.
8. Treat OTel/LGTM and evaluation as adjacent service capabilities. Gate promotion on version-bound contract, functional, tool and security evaluations. Add approved runtime evaluation beside telemetry, with separate data access, identity and spending bounds.

## Authentication constraints

The API validates tokens intended for that API. It checks signature, issuer/tenant, validity, audience and the selected principal/permission contract. Application permission and delegated permission flows are configured separately; a `roles` claim alone does not distinguish them. See [access tokens](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens) and [permission types](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/application-delegated-permission-access-tokens-identity-platform).

Agent ID uses the supported blueprint-to-agent credential flow. A trusted adapter binds the executing agent to an approved child identity and target resource. Blueprint credentials stay outside model context and untrusted agent code. See [Agent ID token acquisition](https://learn.microsoft.com/en-us/entra/agent-id/autonomous-agent-authentication-authorization-flow).

Use OBO only when the service must preserve delegated user authority and the receiving APIs support the approved scopes/consent. Do not replay a middle-tier token to a different audience. See [Microsoft's OBO contract](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow).

For Istio exposure, require effective authorization as well as JWT validation and verify missing-token rejection. See [Istio authentication](https://istio.io/latest/docs/reference/config/security/request_authentication/) and [authorization](https://istio.io/latest/docs/reference/config/security/authorization-policy/).

## Alternatives considered

| Alternative | Disposition |
| --- | --- |
| Each agent calls arbitrary MCP/model endpoints directly | Reject as the default. It prevents a consistent route-policy boundary and makes direct-path control harder to establish. |
| One caller/worker identity shared across all agents and tools | Reject as the default. It obscures per-agent authorization and widens the credential's access. |
| Registry membership is treated as authorization or compliance | Reject. Enforce destination permissions and retain explicit acceptance evidence. |
| Only application-managed authentication | Supported exposure profile where the owning application enforces the required contract and the Gateway/backend paths remain controlled. |
| Only Istio-managed ingress authentication | Supported exposure profile where the mesh configuration enforces the full required contract for the selected API. |
| All calls inherit a signed-in user's authority | Separate delegated/OBO profile. Select it only for use cases that require that authority and pass consent/security review. |
| Observability alone is the release gate | Reject. Operations and quality/security verdicts answer different questions. |

## Consequences

Teams get one reviewed delivery and API consumption pattern with explicit evidence for identity, capabilities and outcome. The platform must operate registry synchronization, policy generation/attachment, identity bindings, a trusted credential adapter, evaluation runners and telemetry correlation. Each is a real implementation responsibility.

Gateway or identity misconfiguration can affect many agents. Version and scope changes, test negative paths, preserve a rollback and keep provider/backend credentials separate. Evaluation must not inherit production write permissions or unrestricted access to private content.

The service retains its existing model garden and runtime while this design is validated. Provider replacement remains a separate decision with its own model/task compatibility and operational evidence.

## Acceptance before status changes to accepted/implemented

- Architecture/identity owners select the exposure and delegation profiles, resource audiences, application roles/scopes and approved agent identity mechanism.
- Flux applies the intended revision and the current graph/runtime and route attachments converge.
- A protected request completes and the exact native skill/tool records and backend execution match the case.
- Allowed and denied caller-to-agent and agent-to-MCP paths are observed, with no backend execution for pre-execution denial claims and no unauthorized direct-path access.
- Registry records bind the exact deployed agent, skill, MCP, model/policy and evaluator versions.
- Release and runtime evaluation evidence appears beside correlated telemetry, with documented data access and cost provenance.
