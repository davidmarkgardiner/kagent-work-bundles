02 · Score and gate

The score explains health. The gate decides action.

A numeric score is useful for trend and communication, but it is not trusted as the automation threshold. The gate uses explicit domain state, complete coverage and consecutive assessments.

Display score: 0–100

healthy = 100 · watch = 80 · degraded = 50 · critical = 0
score = weighted mean of all five domains

Deterministic action gate

Immediate

Any required domain is critical → breach now, even if another domain has incomplete coverage.

Confirmed

A required domain is degraded in two consecutive complete five-minute assessments → breach.

Recovery

Two consecutive complete assessments with every domain healthy or watch → clear the gate.

A score of 90 cannot overrule a critical domain. Incomplete coverage cannot declare recovery.
03 · Daily outcome

Healthy and unhealthy records take different paths.

There is still one daily Kafka record for observability and proof, but only the unhealthy branch consumes model capacity or writes to GitLab.

Healthy day

action: healthy
  1. Daily record reaches Kafka.
    It proves the health loop is alive.
  2. Argo EventSource consumes it.
    The Sensor action filter rejects it.
  3. No Workflow, agent or GitLab call.
    The system stays quiet.

Unhealthy day

action: investigate
  1. Sensor admits one deterministic Workflow.
    A same-day replay hits the same name.
  2. Agent rechecks current worker state.
    At most 12 read-only AKS-MCP calls.
  3. Writer creates or updates one issue.
    Symptoms are grouped beneath the smallest credible causes.

05 · Cluster boundary

No shared filesystem. No shared database required.

The same logical boundary works whether worker and manager are namespaces on one homelab cluster today or physically separate clusters at work later.

Worker plane

  • Fox state-only collectors
  • B1 five-minute snapshots
  • Daily alert controller
  • Vector with Kafka credentials
  • No model or GitLab token

Manager / agent plane

  • Argo EventSource and Sensor
  • Replay-safe Workflow

One cluster now: pass the same Kubernetes context for worker and manager. Two clusters later: move the manager resources and change endpoints/NetworkPolicies—the Kafka contract and security responsibilities stay the same.
06 · Guardrails

The agent can investigate. It cannot quietly become an operator.

Read, decide and write are separate authorities. A prompt is not the security boundary; credentials, tools, RBAC, NetworkPolicy and fixed adapters enforce the shape.

01

Read-only Kubernetes

The agent has only the approved AKS-MCP read tools. No apply, delete, scale, exec, restart or remediation tools.

02

GitLab token isolation

The agent never sees the token. Only the fixed-purpose writer step receives the project-scoped Secret.

03

Default-disabled writing

GITLAB_WRITE_ENABLED=false remains set until Kafka and agent-only proofs pass.

04

One issue identity

Three exact labels identify the managed issue. Zero matches creates, one updates, ambiguity fails closed.

05

Restricted containers

Non-root, read-only filesystems, dropped capabilities, seccomp, bounded CPU, memory and ephemeral storage.

06

Exact egress

Kafka, Kubernetes API, kagent A2A and GitLab egress are scoped to reviewed CIDRs, namespaces and ports.

Does this replace Alloy/Vector?No. It uses the same scope, then compresses current state into a separate daily decision lane.
Does the score trigger tickets?No. The explicit critical/degraded/recovery gate triggers investigation; the score explains the outcome.
Can the agent fix the cluster?No. It investigates and recommends. SRE owns review, change control, execution and rollback.
