# Deploy the repository source on the approved work cluster

When a named AKS cluster is authorized, deploy this folder using the existing kagent, agentgateway, Substrate, and managed Istio installation. Read FRONT-SHEET.md, WORK-BUNDLE-README.md, PLATFORM-PREREQUISITES.md, AKS-ISTIO.md, and LIVE-INTEGRATION.md first. The repository contains the application source, Dockerfile, chart, operator examples, and verification scripts. Do not require a separate ZIP or prebuilt image archive.

1. Confirm the explicit context and installed chart/API versions with read-only checks. Do not switch the global context or upgrade the platform. Report incompatible versions and prepare the smallest reviewed port.
2. Build this source revision through the approved internal image pipeline. Record its registry digest. Keep credentials, private DNS, Azure identifiers, TLS keys, populated values, and rollback material outside this public source.
3. Prefer `existing-agent-istio.yaml.example`. Select a Ready, read-only Substrate-backed agent and its existing model route through agentgateway. Reuse the approved Kubernetes MCP server and discover its exact read-only tool names. Do not replace existing agents, ModelConfigs, routes, Secrets, tool grants, or skill mounts.
4. Reuse the approved Istio Gateway with `ingress.istio.existingGateway`. Deploy the demo VirtualService on an approved hostname with the current certificate and audience/access policy. Keep OTLP internal. Run preflight and deploy through the normal delivery path.
5. Add an approved collector fan-out from kagent, Substrate, agentgateway, and the selected MCP server while retaining the current telemetry destination. Preserve native parent IDs and actor identity. Existing-agent deploy mode deliberately leaves platform releases and OTel configuration unchanged.
6. Submit a bounded read-only Kubernetes MCP prompt through the real HTTPS URL. Run connected verification with the private prompt file, expected tool name, and actual MCP OTel service name. Capture native restore/checkpoint/suspend, observed model/gateway/tool spans, logs, original trace IDs, and the agent result. Report missing server instrumentation as UNKNOWN. Do not manufacture tool or lifecycle spans.
7. For a simulation rehearsal, choose the bundled fixture profile in a separate namespace. Its workflow data and deterministic model are explicitly simulated. Actual sessions, HTTP calls, and OTel still drive the map. Live-model mode in that profile still uses simulated tools.
8. Demonstrate existing skills through their real resulting tool calls. The current diagram has no separate skill node. Claim explicit skill execution only from exported runtime events/spans. If required, implement bounded skill instrumentation and projection tests as described in LIVE-INTEGRATION.md.
9. Record target AKS/Istio versions, Gateway reconciliation, certificate trust, access policy, CNI enforcement, image digests, and rollback location. Report PASS, FAIL, UNKNOWN, and NOT RUN. Local kind/Caddy receipts do not prove AKS acceptance.

The application is a shared single-user POC with bounded in-memory telemetry. Each prompt creates a fresh session. Full sidecar interception and multi-turn restoration are not proven. Do not send messages, publish externally, or change unrelated resources as part of the work deployment.

Implement and present the examples in DEMO-SCENARIOS.md. Start with bounded Kubernetes, Grafana, and GitLab read-only tool checks, then show the combined triage flow. Rehearse the labelled isolation fixture separately. For live Entra isolation, follow ENTRA-ISOLATION-DEMO.md, use the approved identities and protected gateway path, and retain both native gateway denial and zero-backend-delta evidence. Do not treat the UI's internal gRPC prompt call as a protected-front-door test.

For the full identity-isolation showcase, verify two actual agents use their own existing broker-bound identities on MCP egress. Join native actor and gateway principal evidence without exporting bearer values. The standalone initialize probe checks the front door and is not proof that an agent runtime used its assigned identity.

The repository now also contains a dedicated live-tools profile, documented in LIVE-HOMELAB.md. It has a real-model Kubernetes/GitLab homelab proof. Reuse existing workplace MCP infrastructure through the existing-agent profile where available. Treat the lab's short-lived GitLab credential as a proof credential, not an unattended work authentication design.
