# Stage the prerequisites before deployment

This folder carries source and reviewed data, not container images, chart archives, binaries, wheels or credentials. Its main path reuses an already approved Python helper image and projects reviewed code/content through immutable ConfigMaps. No custom image build is required when that compatible image is present. The runtime uses the Python standard library. It does not require the native kagent CLI, Substrate assets, gVisor/runsc or public content downloads.

1. Discover actual cluster architecture, served APIs, KRO/Gateway ownership and compatible kubectl. Review the target's cluster-scoped request and admission-policy capabilities.
2. Inventory and reuse the installed KRO/Gateway/policy controllers and the existing approved Python 3.12 helper image. Verify its internal digest, architecture, `/usr/local/bin/python3`, standard library, CA trust and non-root/read-only execution. Do not assume an arbitrary operator or agent image supplies this interpreter. For Gateway 1.7 upgrade details use the separate `agentgateway-1-7-upgrade` folder.
3. Stage the complete source and pinned data-only content in this folder. The renderer supplies immutable code/content ConfigMaps and fixed Python entrypoints. Confirm approved payload bytes, UID/hash pins and code/mount/command admission enforcement. There is no pip/dependency download or new custom-image build step in this main path.
4. If a compatible approved image or other platform artifact is missing, have its owner stage it through the approved connected acquisition/internal import process first. Verify target-platform destination manifests/digests and retain source/destination provenance, archive checksums and rollback references. A mirror can change manifest bytes; review the actual destination digest. `build/` is an optional alternative for organizations that deliberately choose a custom image; do not make it a prerequisite by default.
5. Render against the verified internal image, approved Gateway/model endpoints, exact namespace/identity profile and actual API-server/CNI paths. Private values and outputs stay outside the source tree. Use existing private registry credentials and CA distribution through their approved owners.
6. Apply platform prerequisites through the existing delivery owner, then the graph and one owner request. Work must not run public image/chart/package pulls, installer downloads or catalog refresh to bypass missing prerequisites.

The lab's existing-image reference is `docker.io/library/python:3.12.12-slim-bookworm`: source OCI index `sha256:593bd06efe90efa80dc4eee3948be7c0fde4134606dd40d8dd8dbcade98e669c`, linux/amd64 manifest `sha256:2986c55feb36e6cae00fa1fefb454283e4b33f35e75ff8bdd123b134130be301`. See `evidence/base-source-provenance.json`. Registry manifest digests and image configuration/cache identifiers are different fields; inspect the actual manifest chain rather than assuming a CLI image ID is interchangeable. This provenance is not proof of an office import. Prefer the compatible approved helper already deployed at work; the office does not need this public repository name or a newly built application image.

The model capability is an existing credential-holding Gateway/backend. The standalone runtime receives no provider key. Have the model owner supply the approved internal destination and canary authority; do not place credentials in settings, the RGD, owner YAML or screenshots.

Live content release/catalog integration and cold import/retrieval are separate target gates when adapting to the office's existing Skill/KnowledgeBase contracts. Included source data and local source/content tests do not establish that delivery path.
