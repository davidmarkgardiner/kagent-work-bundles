01

Protect the agent API and its tool routes.

Start with JWT authentication

Download SVG ↗

The client presents a signed JWT. The receiving gateway validates it and authorizes the requested agent or operation. The agent uses separate credentials for tool and model calls.

→ Request or service call⇢ Identity or credential relationship

Caller authentication

A trusted issuer signs a token for the agent API. The gateway checks its signature, issuer, audience and validity period before applying caller permissions.

Credential handling

This baseline illustrates manually provisioned bearer credentials in Kubernetes Secrets. JWT itself does not require this storage pattern. The platform owner manages expiry, replacement and access.

Service flow

The gateway routes an accepted invocation to the agent. Tool and model calls return through approved gateway routes. Each destination has its own authentication contract.

Presenter cue

First show a protected request. A valid token establishes identity, and policy decides which agent or operation that identity may use. Keep credentials out of instructions and tool results.

02

Replace stored credentials with a federated token exchange.

Add Microsoft Entra workload identity

Download SVG ↗

Keep JWT validation at the API. Change how the calling workloads obtain credentials. AKS projects a short-lived service-account assertion, and a trusted credential adapter exchanges it with Entra for a destination access token.

→ Request or service call⇢ Identity or credential relationship

The handshake

Entra checks a federated identity credential that binds the AKS OIDC issuer, the service-account subject and the assertion audience to a user-assigned managed identity, or UAMI.

What leaves the Secret

The illustrated federated path needs no stored client secret, private signing key or provisioned bearer token in a Kubernetes Secret. Public identity references and trust configuration remain in reviewed configuration.

What remains sensitive

The projected assertion and the returned access token remain short-lived credentials. Keep their mounts and adapter operations unreachable by model-controlled shell or code tools. Same-pod token-file access defeats that isolation.

Separate identities and permissions

Give the caller, agent and MCP backend separate service accounts, identities and grants. The API enforces required application roles or an explicit caller ACL. A token with the right audience alone is insufficient. Entra Agent ID or delegated user access needs a separately reviewed flow.

Presenter cue

The API still receives a JWT. We remove manual credential distribution for this connection. A workload proves its Kubernetes identity, Entra recognizes the configured trust, and the adapter obtains a token for the exact API.

03

Follow a request across the gateway, agent and MCP service.

Add correlated observability

Download SVG ↗

Keep the identity and request paths from view 2. Add OpenTelemetry instrumentation and an approved Alloy or OTel collection path into Loki, Grafana, Tempo and Mimir.

→ Request or service call⇢ Identity or credential relationship⇢ Telemetry

Follow one request

Propagate trace context across supported hops. Record gateway decisions, agent spans, MCP operations, errors and latency. Label every record with the relevant release and operation identifiers.

Collect approved metadata

Drop authorization headers, tokens and credentials before export. Prompt and result content require explicit data-handling approval and redaction. Instrumentation coverage must be verified per component.

Explain usage

Record model-provider usage where reported, with the source and model route. Missing usage stays unknown. Cost requires a versioned price basis and is an estimate until reconciled with billing.

Presenter cue

Now follow the same request through its trace. Logs and metrics explain what happened and where it failed. Those signals do not by themselves tell us whether the answer was correct.

04

Judge behavior against explicit cases and keep reviewable receipts.

Add release and runtime evaluation

Download SVG ↗

Keep the observability layer. Add a release evaluation path and runtime assessments under approved data, identity and spend limits. Bind every verdict to the exact agent, skill, tool, policy and model versions.

→ Request or service call⇢ Identity or credential relationship⇢ Telemetry⇢ Evaluation evidence

Before a release

Run functional, tool-selection, security and quality cases against the candidate. A receipt binds the cases, evaluator, rubric and thresholds to that candidate. Existing review and approval determine promotion.

After a release

Use approved samples or replay cases with known expectations and context. Runtime assessment combines permitted evidence with the evaluation rubric. A trace without an expected outcome is insufficient for a correctness score.

Keep the decision inspectable

Store PASS, FAIL or UNKNOWN with evidence references, hard policy failures and version information. Missing evidence stays UNKNOWN. Findings feed operations and the next reviewed revision, without granting deployment authority.

Presenter cue

Finally ask whether the agent did the right thing. Evaluate a known version against known cases, keep the receipt, and use the result in the existing release review. Runtime findings feed the next change.

Scope and source notes

These diagrams explain a proposed design. They perform no authentication, telemetry collection, evaluation or deployment. The versions retain the gateway, agent, MCP, model garden and reviewed GitOps delivery from yesterday's overview. Registry and skill-catalog details remain in the SCD. This walkthrough does not change their ownership.

The Entra view selects direct AKS Workload Identity federation to a UAMI. It does not imply a distinct Entra Agent ID principal, a delegated user flow, or automatic identity propagation across the gateway. Those paths need their own identity binding, permissions and receiving-service support. Gateway routing does not itself grant downstream access.

The credential adapter is a trusted code component, not a model-callable tool that returns tokens. Model-controlled tools must not read its token mount or execute with its unrestricted identity. The receiving API enforces an application-role or explicit caller-ACL policy as well as JWT validation.

The initial JWT view illustrates manually provisioned tokens as a teaching baseline. JWT authentication can also use automatic token acquisition without Entra. The comparison is about the selected credential lifecycle, rather than a limitation of JWT.
