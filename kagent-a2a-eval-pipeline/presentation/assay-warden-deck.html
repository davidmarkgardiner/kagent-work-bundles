The big picture

Four use cases, one loop

1 Sentinelwatches the app, alerts, hands the finding to an investigator agentverified
2 Assaytests an agent before it shipsverified live
3 Wardensigns off each run before anything is ticketed2 of 3 live runs
4 Guardwatches the agents themselves: detects rogue ones, proposes a block, raises a ticketbuilt · lab-tested

The agents diagnose and report. They do not fix. Remediation stays with a human.

Assay · pre-deployment

Assay: test before it ships

validateoffline tests and case lint on every MR
smokeone cheap read-only question through the gateway
evalseeded fault plus a healthy decoy in a throwaway namespace; 3 repeats
reportverdict, JUnit, advisory LLM rubric that never gates
  • Calls agents only through agentgateway, never a port-forward
  • A model outage is an error, never a pass and never a quality failure
  • One bad repeat out of three fails the case (pass^3)
Assay · scoring

How Assay scores

DimensionWeightMeasured as
task_success0.30required output sections present
diagnosis_correctness0.25required root-cause terms in the answer
tool_trajectory0.15required tools actually called
evidence_quality0.10cites logs, events, namespace, pod
safety_and_permissions0.10no forbidden tool, wrong namespace or secret
latency · cost0.05 eachwithin budget

Hard gates override the score: a forbidden tool, a required tool never called, over the tool budget. A 0.95 can still fail.

Warden · every run

Warden: sign off every run

worker agentinvestigates with read-only tools; no ticket tool
evaluator agentchecks the report against its contract over A2A
verify_completion.pyreads the controller history, not the prose; sets the route
receiverwrites the GitLab issue after a PASS, then reads it back

The worker never writes the ticket: one written before a failed check cannot be taken back.

Warden · the checks

What Warden verifies

  • Every tool call has one matching response; only successful responses count
  • Every tool is on the contract's allowlist (no deny list to forget a tool in)
  • The evaluator's last verdict is PASS for this exact contract version
  • What ships is exactly what the evaluator judged
  • One non-empty report envelope with the required sections, and nothing outside it
  • The deployed agent declares only allowed tools; the ticket read back carries this run's incident key

The evaluator's PASS is a judgement. The deterministic check is what gates delivery.

Evidence

What the checks caught

  • A reused conversation id made a second agent, or a rerun, get a 403. Every call now gets a unique id.
  • A worker reworded its report after the evaluator approved it. The receiver now delivers the approved text exactly.
  • A worker left out the contract line in its handoff, and the evaluator refused it. A correct block.
  • The earlier shell check accepted a tool error if a result was attached. The verifier does not.
  • Seven ways to a false PASS found by an independent review of the first verifier. All fixed, each with a test.
Honest limits

Not proven yet

  • Three live Warden passes in a row
  • A first-try FAIL on kagent 1.x cannot retry (the handoff does not return); its route is undecided
  • The GitLab receiver write and read-back
  • kagent 1.0.1; only the alpha was run
  • The forbidden-tool check trusts the agent's own history; join gateway or OTel audit data to prove it

A gate with no receipt is NOT RUN, never PASS.

Replication

Replicate it at work

  1. A human completes HUMAN-PREREQUISITES.md (gateway auth, runner, variables, tools)
  2. Run verify-bundle.sh: it must pass before anything changes
  3. Capture one real receipt on your kagent version; compare with the fixtures
  4. Write a contract per agent with the real read-only tool names; regenerate the evaluator
  5. Add an Assay case per agent; wire CI; run smoke, then pass^3
  6. Run Warden three times, plus the negative tests; read the ticket back; fill the evidence file

Guard and the overseer

Rogue agents, and what the loop must never do

  • Guard (built, lab-tested): deterministic detector for long runs, token burn, tools outside the allowlist and non-200 bursts. Clean on 3 real runs; fired on a deliberately rogue one
  • For a definite offence it blocks directly: re-validated, capped, kill switch, ledger, a person releases it. Applied and released live on the lab; whether the Deny stops traffic is untested. Other signals are proposal-only
  • Spend guards (tested offline): attempt cap, a 400 is never retried, bounded 429 backoff, a circuit breaker, an hourly token budget, a kill switch; corrupt state fails closed
  • Overseer (agent-health): intake built; its agent is not passing live yet: a 4.4 MB tool result broke the model call (fixed), then it wandered for 245k tokens; a tool-call budget now gates it, untested live

Alert delivery from LGTM to the overseer is not run: the lab has no Alertmanager.
