Where is our agent traffic encrypted?

Trace the real AKS request paths, identify each TLS termination point, and tell us what is configured and what has actually been observed.

Outcome: a hop-by-hop evidence matrix for the secure KRO agent, Istio exposure, Agent Gateway, MCP tools, model routes and observability. No assumption that the proposed architecture matches the deployed environment.

Copyable request

The request is complete on its own. If the copy button is unavailable, select and copy the text below.

Please perform a read-only transport encryption review of our actual AKS agent solution. Trace one representative secure KRO-managed agent end to end using the deployed application endpoint, Istio VirtualService and ingress Gateway, Agent Gateway, kagent Agent, actual model binding, approved MCP service(s), and their backends. Follow the actual implementation; do not assume the proposed architecture has been deployed.

Scope and safety
- Identify the target cluster/context, date, namespaces, components and versions. Use existing authorised read-only access and the organisation's approved repositories and telemetry. Do not change configuration, upgrade, restart, port-forward, run an agent/model/tool request, inject traffic, or perform negative tests unless separately authorised. Do not query, export or print Secret contents, tokens, credentials, conversation bodies or sensitive configuration. Use metadata and redacted fields; keep internal details in approved private channels.
- If target identification, permissions, configuration or runtime evidence is unavailable, report the precise blocker and mark affected hops UNKNOWN. Do not infer workplace proof from lab receipts, a diagram, a Ready status or a successful authentication check.

Map the deployed route
- Start with application -> ingress -> Istio routing -> Agent Gateway -> agent. Then follow agent -> gateway -> each MCP, MCP -> backend, agent -> model gateway -> model garden/provider, agent-to-agent calls, and OTel/log/trace export where they exist. Identify direct paths and proxies and state which paths were not assessed.
- Resolve the actual ModelConfig and RemoteMCPServer references, endpoint scheme, service/port, Gateway/HTTPRoute and Istio VirtualService/Gateway associations. ModelConfig is configuration, not an inference network hop. Check the effective Agent Gateway listener and backend TLS policies, TLS origination and certificate validation against the installed version. Map other model configs or MCPs separately when their paths differ.
- Check the effective Istio PeerAuthentication, DestinationRule, mesh defaults and workload participation (sidecar or ambient where applicable), plus relevant ingress/egress settings. Resolve policy scope, overrides and routing. PERMISSIVE accepts plaintext as well as mTLS; STRICT requires applicable inbound mesh mTLS, but neither alone proves a particular connection. Identify passthrough versus termination/re-origination and the exact encryption endpoints.
- Use existing access logs, proxy telemetry, connection metadata or approved traces to establish negotiated TLS/mTLS and peer identity, TLS version and validation when such evidence exists. Treat configuration, runtime observation, endpoint identity/certificate validation and enforcement against plaintext as separate findings. Do not infer no encryption from an HTTP application URL when mesh mTLS might apply; do not infer encryption from a JWT, private endpoint, network policy, port number, VirtualService or Ready status. A config requiring strict mTLS supports an enforcement claim only to its effective scope; live proof of rejection requires a separately authorised test or existing suitable evidence.

Return
1. An executive answer: what is confirmed encrypted, what is only configured/expected, what is plaintext if established, and what remains unknown. Do not assign a percentage unless all in-scope flows are inventoried and a meaningful denominator is defined.
2. A table with one row per actual hop and direction where relevant: source -> destination; purpose; endpoint/port; app protocol; TLS termination and re-origination points; transport (TLS/mTLS/plaintext/unknown); peer identity and certificate verification; relevant effective policy; configuration evidence; runtime evidence with timestamp; confidence/status; owner and exact next check.
3. A separate list of confidentiality or authentication gaps, prioritised by impact, with the smallest proposed fix and the owner. A recommendation is not approval to implement it.
4. An evidence inventory with private references, time observed, version and access limitations. Redact private hosts, cluster IDs and sensitive identities from any public copy. If you cannot prove a hop, give the specific missing access, configuration or observation needed to close it.
5. Explain whether any sensitive material is visible at ingress/gateway/proxy termination points and whether logs or traces can retain prompts, tool results or tokens. Assess retention and access only if readily available; do not equate encryption in transit with encryption at rest.

How to read the answer

ObservedAn existing, attributable connection observation shows the transport or peer; record timestamp and coverage.
Configured / expectedEffective configuration indicates the intended protection, but the connection has not been independently observed.
Unknown or blockedEvidence is missing, ambiguous or inaccessible. Record the exact reason and next check.
Important: an encrypted hop is not necessarily encrypted end-to-end across gateways. TLS terminators can access plaintext. A plaintext determination requires affirmative evidence; absence of evidence is unknown.

Where practical, include certificate validation and peer identity separately from encryption. A connection can be encrypted but still fail to authenticate the intended server if validation is disabled or misconfigured.

Ask for a concise decision-ready summary followed by the detailed table. The report should carry the environment, collection time, scope and gaps at the top. Use not applicable only when a hop genuinely does not exist; use unknown when it may exist but could not be assessed.
