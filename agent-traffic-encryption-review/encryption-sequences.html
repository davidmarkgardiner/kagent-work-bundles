Identity and encryption across the agent platform

Three views of the same design: how an application gets an agent API token, how an agent gets an MCP token, and which network connections must be checked for encryption.

Design goal: protect every connection carrying agent requests, credentials, tool calls, model data and telemetry. Use TLS or mTLS with peer validation at every boundary, supported by scoped identities and authorisation.
Solid green: target protected flowEach gateway may terminate and establish a separate protected connection

1. Application UAMI → agent API

This example assumes the caller runs in AKS and uses direct Workload Identity federation. Another caller environment or an AKS identity-binding proxy changes the token-acquisition sequence. The UAMI is the caller identity; it is not the agent's identity.

  • AKS supplies a projected service-account assertion to the workload. The application exchanges it with Entra over HTTPS, using its UAMI's identity and requesting a token for the agent API.
  • Entra verifies the assertion using federation and the AKS OIDC issuer. Discovery/key retrieval is conditional, not necessarily a fresh call for each request.
  • The receiving API / Gateway validates the token and authorises the caller at its actual configured enforcement points. The application-to-ingress TLS termination shown is an illustrative profile; passthrough or an upstream terminator changes it.

2. Agent UAMI → MCP tool

This is the per-agent UAMI alternative, not a claim that the SCD's Agent ID / trusted-adapter path is already deployed. The agent obtains a distinct token for the MCP API. The MCP server separately owns its backend identity.

  • The agent's service-account assertion is exchanged for an Entra token targeted to the MCP resource; do not replay the caller's agent API token.
  • The gateway applies its configured caller and tool policy. Whether the MCP server validates a token itself or trusts gateway-provided identity is an explicit receiving-system decision.
  • The workload or its approved credential component needs access to the projected assertion. A component in the same pod is not automatically isolated from other processes with access to that token.

3. HTTPS and internal traffic

The desired sequence protects every separate connection and return path. Select the real route, establish where TLS terminates, and validate the identity and certificate at each boundary.

One HTTPS endpoint does not prove end-to-end encryption. An Istio VirtualService routes traffic; its associated Gateway may terminate or pass through TLS. Internal Istio mTLS can protect traffic between participating proxies even when the application uses HTTP, but it must be verified. TLS terminators can see plaintext.

4. Building the secure target

This target pattern assumes the workloads participate in a supported Istio mesh and the model route passes through Agent Gateway. Assess other route and identity profiles using the same security requirements.

What the mesh protects: the network between participating proxies. Applications and proxies can see plaintext at TLS termination and within a pod; this is hop-by-hop encryption, not uninterrupted application-to-application encryption. Use application TLS as an additional layer where that stronger property is required and supported.

Controls to put in place

  1. Enroll and identify workloads. Select a supported mesh mode, include ingress, Gateway, agents and MCP services where compatible, and provide managed workload certificates with rotation. For the managed AKS Istio add-on, use its installed revision-specific injection configuration and check data-plane interception.
  2. Require internal mTLS. Use scoped Istio PeerAuthentication STRICT for covered destination workloads after compatibility testing; use supported outbound auto-mTLS or explicitly configured traffic policy. Apply authorization rules for the intended peer identities and operations. Keep bypass and excluded ports in the review.
  3. Protect non-mesh and external connections. Use native HTTPS or TLS origination with trusted CA and hostname verification; use client certificates where the receiving contract requires mTLS. Protect collector/exporter connections, MCP backend connections, and Kubernetes API and identity-service calls too.
  4. Use distinct identities. Give callers, agents and MCPs their own least-privilege identity and destination-specific token audience; use workload federation where supported. Retain route/tool authorization and network boundaries alongside encryption.
  5. Prove each path. In a non-production environment, record the negotiated transport and peer principal for every hop, exercise the real agent/MCP/model route, demonstrate rejection of plaintext at strict destinations, validate certificate failure handling and rotation, and document rollback.

Is it possible on AKS?

Yes, in principle. Istio supports service-to-service mTLS, and the AKS Istio add-on supports an Istio sidecar-based mesh. Whether this exact agentgateway, kagent and MCP deployment is compatible needs version-specific review and a non-production rehearsal. The add-on currently does not support ambient mode; do not assume an ambient deployment is available merely because upstream Istio supports it. Another approved mesh or application-level TLS can be assessed against the same boundaries.

For a safe migration, inventory existing clients and exclusions; test proxy participation and connectivity first, then stage enforcement from permissive to strict in a suitable scope after owners approve. Validate certificate trust, traffic interception, health probes and egress, and prove an authorized real request, peer identity, denial of a non-mesh plaintext client, and rollback in a non-production environment. Do not change the live workplace system as part of the current read-only review.

What we need to do

  1. Inventory each service, route, identity and namespace; map every connection that carries credentials or agent data.
  2. Configure and test TLS or mTLS for each connection, including certificate trust, authenticated peers, enforced policy and denial of plaintext.
  3. Choose the approved workload identity profile; establish separate destination audiences and authorisation for caller, agent, MCP, model and telemetry.
