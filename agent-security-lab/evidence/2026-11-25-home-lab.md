# Home-lab receipt — 25 November 2026

Scope: dedicated VM and kind cluster, not AKS. Results are from actual runtime checks; the lab uses synthetic test workloads and no provider credential.

## Installed and ready

- kind Kubernetes 1.37.0; kagent 1.0.1; release-matched Substrate 1.0.0; Istio 1.31.4; Agent Gateway 1.7.0; KRO 0.9.4; Gateway API 1.6.0.
- kagent installer reported success; controller, PostgreSQL, tools, UI and gVisor worker were running; `kagent-default` WorkerPool showed one ready replica.
- KRO `AgentSecurityCanary` reconciled an `api.kagent.dev/v1alpha3` AgentTemplate and Agent. The graph and Agent reported Ready, including the substrate golden snapshot. This is a tool-free canary, not the existing secured 0.x KRO implementation.

## Traffic observations

1. The standalone mesh script returned PASS after HTTP 200, destination-side mTLS counter increase `2 → 3` for the expected client/server principals, and reset/200/reset for STRICT/PERMISSIVE/STRICT plaintext controls.
2. The native Istio-integrated Agent Gateway reached the same STRICT backend over mTLS. A subsequent scripted check recorded its exact gateway/server principal counter increasing `1 → 2`; the separate test client-to-Gateway leg was HTTP.
3. A lab caller connected to an HTTPS Agent Gateway using a trusted self-signed lab certificate and matching hostname. An unrelated CA failed verification (curl exit 60); missing token returned 401; a short-lived Kubernetes service-account JWT with the specified audience returned HTTP 200 and the expected canary agent card. Destination-side TCP mTLS bytes for the exact gateway/controller principals increased `1110 → 1295`. This proves that request path to the controller; it does not prove an executed agent task.

4. A separate KRO-created fixture agent sent an A2A `SendMessage` through the HTTPS gateway and completed on Substrate with `LAB_FIXTURE_OK`. The fixture server logged a `POST /v1/chat/completions`; its destination metric showed the gateway-to-fixture mTLS count rising `1 → 2` with the exact gateway and fixture workload identities. The model is a deterministic protocol fixture, not a real LLM. The ModelConfig route from Substrate egress to the model gateway uses HTTP and requires a separate security fix and proof.

## Failures and recovery

- First kagent install failed during CRD installation with etcd request timeouts while the node was under storage/image-pull load. The release was left failed with partial CRDs. After inspecting the release, CRDs, readiness and etcd latency, a single installer continuation succeeded. Future automation stops on failure and does not automatically retry.
- Gateway API application timed out on the backend TLS CRD; the missing object was identified against the exact upstream v1.6.0 manifest and applied separately. A later complete checksum-verified `install-gateway` run succeeded.
- The initial agent-card checker expected the Kubernetes hyphenated name, but kagent 1.x advertises an underscore-normalised card name. The check was corrected and passed.
- The first agent mTLS checker used a two-second metric read; TCP metrics had not flushed yet. It now waits up to 30 seconds for a fresh byte increase and passed.
- On clean kind nodes, container DNS inherited an unusable loopback stub. The lab-only DNS step copied the VM upstream resolver to the kind node and restarted only the new cluster's CoreDNS.
- Injecting an Istio sidecar into the Substrate egress Agent Gateway caused its readiness server to fail with an address-in-use error. Changing the sidecar status-port annotation did not resolve the failure. The lab experiment was rolled back; a supported transport configuration still needs investigation.
- The bootstrap script initially stopped because cloud-init reported completed with deprecation warnings and returned exit code 2. After limiting acceptance to deprecation-only warnings, the script completed on the already-prepared VM and verified all four binary checksums. This is not a clean-VM rebuild test.

## Scope limits

No real-provider model call, MCP call, UAMI exchange, ingress/VirtualService test, controller plaintext denial, certificate rotation or CNI NetworkPolicy enforcement was tested. The HTTPS listener terminates TLS at Agent Gateway; mTLS protects the following gateway-to-controller network hop. The kagent controller's default server auth remains insecure and direct backend reachability has not been blocked. This is a lab capability demonstration, not production readiness or workplace proof.
