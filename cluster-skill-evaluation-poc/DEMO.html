Where labels go & what happens to the MR

GitLab calls these merge requests (MRs), equivalent to the PR term. The ordinary evaluate-skill label requests work; it grants no backend permissions. Labels attach to issues or MRs, never branches.

Credentials, policy & the release boundary

Read-only intake reads the request and exact source revision. A separate scoped GitLab writer workflow owns MR write authority. The agent requests an action; the workflow account executes it. Candidate skill content cannot replace the platform acceptance policy, choose a runner image or expand permissions.

Full raw evidence stays private. The MR receives a sanitized receipt and a bounded artifact link; raw traces and secrets are never committed to GitLab. This demo creates no real MR or artifact.

Before writing results, recheck the current branch head. Before merge/release, ensure skill content matches the tested content and pinned policy. Merge or squash can create a new SHA: integration changes require retesting. Passing is not human approval. The evaluator never deploys production.
